# TTS：流式合成、首包、音色

> 状态：草稿
> 最后更新：2026-10-01

这一页讲 agent 视角下的 TTS：文本怎么进、音频什么时候出来、音色怎么固定、中文要额外处理什么。声学模型和声码器的结构只在影响这几件事时提到。

---

## 1. 核心概念

### 1.1 三种"流式"

"支持流式"这个说法太含糊，要区分文本侧和音频侧：

| 形态 | 文本怎么进 | 音频怎么出 | 首包取决于 | 例子 |
|---|---|---|---|---|
| 非流式 | 整句 | 整句合成完一次给 | 整句合成时长 | 小智服务端的非流式 provider 基类；CosyVoice 官方 FastAPI / gRPC 示例（没开 `stream=True`） |
| 单句内音频流 | 整句 | 边合成边吐块 | 模型产出第一块需要的计算量 | CosyVoice `stream=True`；CosyVoice2/3 的 Triton + TRT-LLM 部署 |
| 双流式（文本流入） | LLM 的 token 增量直接送入 | 边合成边吐块 | 模型攒够多少文本才开始出声 | Kyutai TTS（unmute 逐词送）；CosyVoice2/3 的 bistream（只在本地 Python API 里有，不能和 vLLM 同用）；小智服务端里的几家云端双流式 TTS |

还有一种名义上流式、实际整段出的情况：fish-speech 本仓库服务的 `streaming=True` 按批次出，不带 speaker 标签时整段文本只算一个批次，首包等于整段合成时间。**看到"流式"要去代码里确认第一块音频到底什么时候产出。**

### 1.2 首包延迟

首包（TTFA，time to first audio）= 文本到达 TTS → 第一块可播放的音频。口径上要注意：

- **从哪开始算**：发请求时刻，还是参考音频编码之后？FireRedTTS2 仓库里的计时从参考 token 化之后开始，不含参考音频编码和音频解码，比端到端口径乐观。
- **到哪结束**：第一块数据，还是第一块"有声"的数据？很多模型开头有一段静音，实战里应该裁掉首部静音再计时。
- **第一块数据是不是音频**：社区测试里出现过把控制帧当首音的情况。
- **并发**：首包随并发恶化得很快。CosyVoice2 + TRT-LLM 在 L20 上首块 P50：并发 1 约 185–218 ms，并发 4 约 0.9–1.2 s（仓库自述）。CosyVoice3 只有并发 4 的数字（P50 740 ms）。

仓库自述的几个量级（都没有复现，口径各异）：CosyVoice3 README "as low as 150ms"（未说明硬件和口径）；FireRedTTS2 "as low as 140ms"（L20）；unmute 的 "TTS latency" 单卡 L40S 全部服务同机约 750 ms、分卡约 450 ms。对中文儿童短句、单并发、自托管的首包目标，实战笔记里设的是 P50 ≤ 0.4 s，**能否达到待确认**。

影响首包的结构性因素：

- **首块需要多少语音 token**。CosyVoice 本地 Python 版首块要 `25 + pad + 3` 个 token（25 Hz），推算要先生成 1.1–2.1 s 的音频（推断，待确认）；Triton 版首块是 15 + 3 个 token，更激进。VoxCPM 约 160 ms 一块、FireRedTTS2 80 ms 一帧，首块在结构上只需要 prefill 加一两步。
- **参考音频的 prefill**。零样本克隆每次调用都要处理参考音频和参考文本。把说话人特征提前缓存可以省掉一部分：CosyVoice2 Triton 版开说话人缓存后首块 P50 从 218 ms 降到 185 ms（仓库自述）。
- **建连**。云端 TTS 的建连时间也在关键路径上，unmute 的做法是 TTS 建连和 LLM 请求并行，拿到第一个词时才等连接就绪。

### 1.3 分句送入

LLM 是流式出 token 的，大多数 TTS 却按"句"合成，中间要有一个切分器。切分决定了首包前要等多少文本：

- **首段要短**。小智服务端基类的做法是首句碰到逗号就切，之后碰到句号类标点才切。实战笔记里的一组起点：首段遇到 `。！？；，、` 且累计 ≥ 6 字就切，或累计 12–15 字时强制在最近的标点切；后续按句号类标点切，每段 20–40 字。
- **不能太短**。CosyVoice 在分段文本短于参考文本一半时告警 "may lead to bad performance"；社区也报告过某些模型在很短的句子上合成失败。所以首段长度要和参考文本长度一起调。
- **TTS 自带的切句是为离线质量设计的**。CosyVoice 内置切句每段 60–80 字、默认不按逗号切，整段送进去时第一段可能长达 60–80 字。agent 里必须自己切。
- **逐字送只对支持文本流入的模型有意义**。unmute 逐词送依赖 Kyutai TTS 本身支持文本流入；对整句接口逐字送，每次都要重新 prefill，还会丢掉句间韵律。中文没有空格，"逐词"本身就要先分词。

分句的另一个作用是**对齐**：开源 TTS（CosyVoice、fish-speech 等）都不输出字级时间戳。短语级调用时，每次调用对应一个已知短语，把各块时长累加就得到精确的短语边界，句内再按字数插值，这是"按已播放位置截断上下文"的最低成本做法。

### 1.4 音色克隆

| 方式 | 输入 | 例子 |
|---|---|---|
| 零样本克隆 | 一段参考音频 + 对应文本 | CosyVoice：参考音频 ≤ 30 s，需要参考文本（cross-lingual 模式不需要）；fish-speech：参考音频通常 10–30 s |
| 说话人缓存 | 把参考音频算好的特征存成 id | CosyVoice `spk_id` / `spk2info.pt`；fish-speech `reference_id` 和内存缓存 |
| 指令控制 | 用文本描述情感、语速、方言 | CosyVoice `inference_instruct2`；fish-speech 内联 `[whisper]` 一类标签 |
| 微调 | 几十分钟以上的目标语料 | CosyVoice 有完整训练 recipe；fish-speech 的 LoRA 默认配置"基本只会学到发音方式，不包含音色" |

agent 里音色的关键是**一致**，"像不像某个人"排在后面：

- 模型自己的话、预合成的提示语、本地合成的播报，要是同一个声音。离线提示语和在线合成要用**同一个模型、同一份说话人缓存、同一个版本**。
- 采样随机性会让每次合成的韵律不同，可以固定随机种子（CosyVoice 示例用 `set_all_random_seed`；fish-speech 有 `seed` 字段）。
- 用 S2S 上游的输出做克隆参考时，下行编码的失真会一起被克隆，而且要先确认上游服务条款是否允许。

许可也要提前看：fish-speech 的 Fish Audio Research License 商用必须另签授权；CosyVoice 代码是 Apache-2.0，权重许可仓库里没写（待确认）。

### 1.5 中文 TTS 的特殊点

- **文本规范化（TN）必须有，而且要在自己这层做一道**：
  - CosyVoice 有前端（`ttsfrd` 可选，`wetext` 默认），但**文本流入模式和含 `<|…|>` 的文本会跳过 TN**；
  - fish-speech 推理路径上没有 TN，`normalize` 字段没被用到；
  - FireRedTTS2 只做符号清洗，不读数字。
- **数字读法**：同一串数字在不同语境读法不同，"2025 年"逐位读、"2025 元"按数值读、"10:30"是时间、"3/5"是分数、"第3关"是序数，电话号码和编号要逐位读、"1"常读作"幺"。儿童内容里 `3/5`、`10:30`、`2km`、`第3关` 这类写法各模型读得对不对待确认，需要专门的 TN 测试集。
- **多音字**：行（xíng / háng）、长（cháng / zhǎng）、重（zhòng / chóng）。模型自己会猜，猜错时的补救手段是拼音标注：CosyVoice 支持 `[j][ǐ]` 这种拼音纠音，IndexTTS 支持拼音 / 音素纠音。角色名、景点名里的多音字要建一张发音表。
- **流式时 TN 不能切碎**：数字、单位要按整词替换，避免 `12` 被拆进两个 delta 后分别规范化。
- **标点替换的副作用**：CosyVoice 中文分支把英文 `.` 统一换成 `。`，含中文的文本里的小数点、URL、版本号会受影响（wetext 是否先把 `3.5` 转成"三点五"待确认）。
- **要过滤的东西**：Markdown 符号、emoji、URL、ID。LLM 输出里很常见，TTS 会念出来或念出奇怪的停顿。

## 3. 常见坑

- **把 README 的首包数字当成自己的首包**。口径、硬件、并发、是否含参考编码都不一样，必须按自己的口径（文本到达 → 首块有声 PCM）实测。
- **直接用官方示例服务**。CosyVoice 的 FastAPI / gRPC 示例没开流式，整段合成后再分块吐。
- **共享模型实例的隐藏状态**。CosyVoice 本地流式代码里 `token_hop_len` 改的是实例属性，疑似第一次流式请求后首块门槛一直停在最大值，并发请求也会互相影响（推断，待实测确认）。
- **首段太长**，用 TTS 内置切句，第一段 60–80 字。
- **首段太短**，比参考文本一半还短，质量下降或合成失败。
- **提示语库和在线合成用了不同的模型版本或说话人缓存**，同一个角色出现两种声音。
- **非流式参数在流式下不生效**：CosyVoice 的 `speed` 只在非流式下生效。
- **忘了 TN**，或者以为 TTS 模型"自己会读数字"。
