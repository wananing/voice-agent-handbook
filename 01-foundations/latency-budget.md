# 延迟预算：一轮对话的时间分解

> 状态：草稿
> 最后更新：2026-10-01

语音 agent 和文本 agent 最大的差别是**时间成了架构的一部分**：用户说完一秒多还没听到声音，就会以为设备坏了。这一页把"用户停止说话 → 听到第一个字"拆成几段，给出各段的量级来源，再看级联、半级联、S2S 三种链路里这条预算分别长什么样。

本页的数字分三类，引用时要分清：

- **实测样本**：来自一份实践笔记（一个儿童伴游玩偶项目的设计笔记，未发布），按键说话、上行 Opus、中文，从**松键**起算。样本量小，只代表那套环境，不是厂商指标。
- **仓库自述**：README 或文档里的数字，本手册没有复现，口径各异。
- **推算 / 待确认**：从代码或参数推出来的，没有实测。

---

## 1. 核心概念

### 1.1 起点和终点

- **起点**：用户真正停止说话的时刻。开放麦克风场景下系统并不知道这个时刻，只能事后从音频里找；按键说话场景通常用**松键**近似（用户可能说完后过一会才松键，这段不计入）。
- **终点**：用户听到第一个字。要区分两种"首音"：
  - **有声音**：任何声音，包括"我查一下路线"这类提示语；
  - **有内容**：回答本身的第一句。
  
  两者混在一起会自欺：提示语能把"有声音"提前，但不能冒充"有内容"。

实测样本里的产品约束可以作为参照：首个有内容的句子 ≤ 2.5 s，目标约 1 s；超过 2 s 没声音，用户认为设备失灵；首句到正文的空档 ≤ 1.5 s。

### 1.2 一轮的时间分解

以级联链路为例：

```
用户停止说话
  │ ① 判停：确认用户说完了
  │ ② ASR 定稿：冲刷尾巴，拿到 final 文本
  │ ③ LLM 首 token（以及攒够第一段可合成的文本）
  │ ④ TTS 首包：第一块可播放的音频
  │ ⑤ 网络：下行首包到达设备（上行最后一包也在 ①② 里）
  │ ⑥ 播放缓冲：解码、凑够预缓冲、送进扬声器
  ▼
用户听到第一个字
```

各段的量级和来源：

| 段 | 量级 | 来源与说明 |
|---|---|---|
| ① 判停 | 按键说话：约 0（松键即结束）<br>开放麦克风：几百 ms 到数秒 | 框架默认值：Pipecat VAD `stop_secs=0.2`，之后跑一次 smart-turn（README 自述多数云主机 < 100 ms），判"未说完"时最多再等 3 s；LiveKit 端点等待 `min_delay=0.5 / max_delay=3.0`（接流式检测器时 0.3 / 2.5）；TEN VAD 扩展静音 1000 ms；FunASR 内置 FSMN-VAD 尾部静音 800 ms。详见 [判停](../03-mechanisms/turn-detection.md) |
| ② ASR 定稿 | 实测样本：上游"提交 → 识别完成"约 0.37 s<br>自托管离线短句：推算 0.1–0.3 s（待确认） | 流式 ASR 要冲尾巴：sherpa-onnx 要灌 0.3–0.8 s 尾部静音（计算比实时快，但算在这一段）；Kyutai STT 固定延迟约 0.5 s。见 [asr](asr.md) |
| ③ LLM 首 token | 实测样本：最小档位、关闭思考、前缀缓存的策略模型，首 token 约 0.5 s<br>S2S 工具回合"回传结果后再生成一轮"约 1.2 s | 首 token 之后还要攒够首段文本（例如 ≥ 6 字）才能送 TTS，这段取决于输出速度，量级待确认。社区报告（小智性能测试）里有 qwen2.5-72b vLLM 首 token 0.601 s 一类数字，但测试没带 tools、口径偏乐观 |
| ④ TTS 首包 | 仓库自述：CosyVoice2 + TRT-LLM，L20 单并发首块 P50 185–218 ms；unmute 单卡同机约 750 ms、分卡约 450 ms<br>自托管中文目标：P50 ≤ 0.4 s（能否达到待确认） | 并发上去后恶化很快：CosyVoice2 并发 4 时首块 P50 约 0.9–1.2 s（仓库自述）。见 [tts](tts.md) |
| ⑤ 网络 | 待确认 | 取决于 RTT、是否需要建连（TLS 握手）、上行组帧（Opus 20–60 ms 一帧）。建连要提前做，不要放在关键路径上 |
| ⑥ 播放缓冲 | 几十 ms 到几百 ms | WebRTC 客户端缓冲一般只有几十 ms；WebSocket 设备侧看实现：小智服务端前 5 包（300 ms）直发作预缓冲，设备是否等满再播待确认。解码帧 20–60 ms |

两个不在上表但经常出现的段：

- **工具执行**：实测样本里状态类工具是内存计算，+1–50 ms；要调后端的写操作可到秒级。
- **话术 / 策略决策**：级联里如果先跑一个小模型选动作，这一段在 ③ 之前。

### 1.3 预算怎么用

- **先看哪段在关键路径上**。并行起来的段不算：例如 TTS 建连和 LLM 请求并行（unmute 的做法），说话人特征提前缓存，正文生成和首句播放并行。
- **按 P50 和 P90 两个口径记**。并发、冷启动、缓存未命中都会把尾部拉长。实测样本里，S2S 上游更新会话配置导致缓存作废时，首音多 80–200 ms（每轮都更新则多 150–270 ms）。
- **每段单独打点**。unmute 的压测把延迟拆成 stt / vad（判停 + 冲刷）/ llm / tts_start 几项，这个拆法可以直接用作 trace 字段，见 [评测](../03-mechanisms/evaluation.md)。

## 2. 三种链路里的预算

### 2.1 级联：ASR → LLM → TTS

```
判停 ─► ASR 定稿 ─► LLM 首 token ─► 攒首段 ─► TTS 首包 ─► 网络 ─► 播放
```

- 段数最多，每一段都在关键路径上。
- 好处是每一段都可控、可替换、可并行优化：策略层只输出动作，一出结果就并行启动正文生成，首句先播。
- **实测样本**：按键说话，级联链路普通回合首音 P50 1.4 s；工具回合因为正文是投机生成的，有内容首音也是 1.4 s。
- **粗估（待确认）**：unmute 笔记里对"自托管级联、按键说话"的粗估是 STT 定稿 0.1–0.4 s + LLM 首词 0.1–0.8 s + TTS 首包 0.45–0.75 s，合计约 0.7–1.5 s。

详见 [级联](../02-architectures/cascade.md)。

### 2.2 半级联：实时模型出文本，自己 TTS 出声

```
判停 ─► 音频 LLM 首 token（省掉独立 ASR）─► 攒首段 ─► TTS 首包 ─► 网络 ─► 播放
```

- 省掉 ASR 定稿这一段，但多了自己 TTS 的首包；音频 LLM 的首 token 包含整段音频的编码和 prefill。
- 声音由自己的 TTS 出，模型的话、提示语、本地播报可以是同一个音色。
- **没有实测样本**。调研笔记里给的实验目标是端到端首音 P50 ≤ 1.1 s（这是目标，不是测量值）。Qwen3-Omni cookbook 里有一条 vLLM 日志：含工具定义的请求从 prefill 到输出工具调用约 0.56 s，GPU 型号未标，只能当参考。

详见 [半级联](../02-architectures/half-cascade.md)。

### 2.3 S2S：语音进语音出

```
判停（常在服务端）─► 模型首个音频块 ─► 网络 ─► 播放
```

- 段数最少，普通回合最快。判停通常由上游服务端做，可能关不掉。
- **实测样本**（从松键起算）：
  - 全双工 S2S + 原生 function call，普通回合首音 0.87–0.96 s；
  - 角色 S2S + 外置判定层，普通回合 P50 1.2 s；
  - **工具回合反而最慢**：提交 → 识别完成约 0.37 s，→ 模型给出 function call 约 0.8 s，→ 执行工具 +1–50 ms，→ 模型再生成并合成出第一个有内容的音频约 2.1 s。最后一段"再生成一轮"约 1.2 s，占了大头。
  - 在 function call 那一刻本地播一段预合成提示语，"有声音"提前到 0.87 s 左右，"有内容"仍是 2.1 s。
- **仓库自述**：Moshi 理论延迟 160 ms（80 ms 帧 + 80 ms 声学延迟），L4 上实际低至 200 ms。全双工模型没有独立的判停段，口径跟按键说话的数字不可直接比较。

详见 [S2S](../02-architectures/s2s.md)、[全双工](../02-architectures/full-duplex.md)。

### 2.4 对比

| | 级联 | 半级联 | S2S |
|---|---|---|---|
| 关键路径上的段 | 判停、ASR、LLM、TTS、网络、播放 | 判停、音频 LLM、TTS、网络、播放 | 判停、模型、网络、播放 |
| 普通回合首音（实测样本，松键起） | P50 1.4 s | 无实测 | 0.87–0.96 s（全双工 S2S）；P50 1.2 s（角色 S2S） |
| 工具回合有内容首音（实测样本） | 1.4 s（正文投机） | 无实测 | 2.1–2.3 s |
| 主要优化手段 | 并行、投机生成、首段短切、建连并行 | 同级联的 TTS 侧手段 | 提示语占位、让结果不经过模型再生成 |

一个反直觉的结论：**S2S 的普通回合最快，工具回合却最慢**，因为工具回合多走一圈"回传结果 → 模型再生成"。选链路时要按自己的回合构成（闲聊多还是工具多）来算。

## 3. 常见坑

- **口径不一致就比较**。松键起算和"用户停止说话"起算、有声音和有内容、首块数据和首块有声音频，差别可以有几百 ms。
- **把仓库自述的首包当成自己的预算**。硬件、并发、是否含参考音频编码都不同，见 [tts](tts.md)。
- **只看 P50**。P90 往往由冷启动、缓存失效、并发排队决定，用户记住的是最慢的那几次。
- **把提示语当成首音优化的终点**。它解决的是"有声音"，不是"有内容"。
- **忘了冲刷段**。ASR 灌尾部静音、延迟流 ASR 的固定延迟，都在关键路径上。
- **建连放在关键路径上**。TTS、上游会话的建连应提前或与 LLM 请求并行。
- **判停等待被默认值决定**。开放麦克风下框架默认的 0.5–3 s 等待可能比其他所有段加起来都长。
