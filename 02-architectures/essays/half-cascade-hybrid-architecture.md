## 0. 结论先行

**能平衡，但平衡发生在"按回合分流"这一层，不在某一个模型里。** 没有一个模型同时是最快、最聪明、最自然的：S2S 普通回合最快、最自然，但出声前没有文本、工具回合最慢；文本路径（级联 / 半级联）可审核、工具回合反而快、智力可以换成任意大模型，但普通回合多一段 TTS 首包、失去原生表现力（架构 §3.2 三角权衡表）。混合架构做的事是：**每个回合按类型和风险选一条路**，让寒暄走快而自然的路，让事实、方案、工具走可审核、聪明的路（KM 1.1）。

这件事成立有四个前提，**缺一不可**：

| # | 前提 | 缺了会怎样 |
|---|---|---|
| 1 | **声音统一**：S2S 原生声音与 TTS 声音听不出是两个人，或者所有话都走同一个 TTS | 用户听到两个角色；"切换"本身成了最大的不自然（BP B.6-2："只是把音色割裂从一处挪到另一处"） |
| 2 | **一份上下文**：无论这一回合走哪条路，下一回合看到的历史是同一份、且是用户实际听到的 | 指代错乱（"你刚才说的那个"指不上）、重复调用、两边各说各话 |
| 3 | **路由器**：由规则（阶段、意图类别、工具注册表路线）决定每回合走哪条路，模型只能提议 | 分流失控：高风险内容从 S2S 直出，或者所有回合都退到慢路 |
| 4 | **上游能力位**：按回复选模态、静默收口、是否自动续答等能力已被 P0 探针确认 | 设计好的路线在该上游上根本走不通（例如自动续答的上游无法"结果本地自己念"） |

三种可行的混合形态（§2）：**(a) 同一上游按回复选模态**、**(b) 前台 S2S + 后台文本 LLM**、**(c) 音频 LLM 出文本 + 文本层（+ 大文本 LLM 兜难题）+ TTS**。(a)、(c) 天然一份上下文；(b) 智力最强但两份上下文、延迟陷阱最多。推荐（§5）：A 类近期 (b) 的"本地 TTS 出声"变体，能力位允许时用 (a) 替换其中的文本回合，长期升级到 (a)+(c) 同模型；B 类近期级联为主，半级联理解端验证通过后换成 (c)，S2S 只在 (a) 可用时用于低风险回合。

## 1. 定义与三层次

"端到端"有三个层次，控制点从少到多（KM 2.10；E2E §1）：

| 层次 | 链路 | 判停 | 工具 | 上下文 | 出声前文本 |
|---|---|---|---|---|---|
| 真全双工 | 双流同时听说（moshi、MiniCPM-o） | 不存在判停事件，模型每 80 ms 自决 | 无 | 最差 | 文本只早约 80 ms，等于没有 |
| 半双工 S2S | 服务端判停后轮流说（OpenAI / Gemini Live、Qwen Omni Realtime、StepAudio 3、Doubao） | 服务端，能否关看厂商 | 原生 FC | 中，靠 session.update / 条目注入 | 只早几十毫秒（04 `output.text_lead_ms`） |
| **半级联** | **音频理解端只出文本 → 文本层 → TTS** | 完全自控 | 等于底座能力（原生或提示词） | 最好，就是 chat messages | 整句，可挂护栏钩子（04 §6.4） |

半级联的理解端有两类来源：云 S2S 设成只出文本（OpenAI `modalities=["text"]`、Ultravox `output_medium="text"`，LK-B §4.1；PC-B §4），或自托管音频 LLM（Step-Audio 2 mini、Qwen3-Omni Thinker、ultravox，HC §1）。真全双工不进候选：无工具、无审核窗口（E2E §3.1）。

**半级联和级联的差别**只有三点，其余（判停、上下文、缓存、截断、护栏、声音）两者相同（04 §6.5）：

1. **省掉 STT 一跳**：音频直接进理解端；省下的是 ASR 定稿的尾巴，多出的是编码器处理整段音频的时间（E2E Q3【推算】）。Step-Audio 约 12.5 token/s，5 s 的话约 63 个 token，预填充可忽略（HC Q1b【推算】）。
2. **保留一部分副语言**：但要看训练目标。ultravox 是 KL 蒸馏（"模仿读了转写稿"），副语言没有训练目标支撑；Step-Audio 2 mini 有公开副语言评测，平均 80、年龄 94、情绪 82（仓库自述、自家评测集）；Qwen3-Omni 只有定性示例（HC Q4）。
3. **没有用户转写**：理解端不产出 user 文本，历史要文本就得另跑转写（§2(c) 坑与办法）。

## 2. 三种混合形态

### (a) 同一上游，按回复选输出模态

```
用户音频 ──▶ 上游（一个会话 / 一份 messages）
               │ request_response(modality=audio) ──▶ 原生语音直出（寒暄、安抚）
               └ request_response(modality=text)  ──▶ 文本 ─▶ 出声前护栏 ─▶ 本地 TTS（事实、工具结果、自己的话）
```

| 项 | 内容 |
|---|---|
| 上下文份数 | **1**（上游会话；本地镜像只作重灌源，KM 3.4） |
| 声音 | 两种：原生声 + TTS 声，除非 TTS 克隆到接近；Step-Audio 可两路都用同一参考音（token2wav `prompt_wav`，HC Q1b） |
| 延迟：普通回合 | 走音频：闭源 S2S 0.87–0.96 s（实测）。走文本：理解端首个文本 token + TTS 首包，未实测 |
| 延迟：工具回合 | function call 约 0.8 s（实测）→ 执行 → 结果直念 ≈ 1.1 s（03 A1，推算）；或请求一次文本模态续答 = 0.8 s + 工具 + 文本 TTFT + TTS 首包（未实测）；都避开"回传 → 再生成音频"约 1.2 s（实测） |
| 智力来源 | **同一个模型**。(a) 换来的是可审核性和声音控制，**不提升智力** |
| 依赖的能力位 | `output.modality_switch = per_response`；`tools.silent_close ≠ none`；`history.text_flips_modality`（最好 `no`）；文本模式下 `cascade.pre_speech_hook = sentence`（04 §2.2.10、§6.5） |
| 代表实现 | OpenAI Realtime：每次 `response.create` 可带 `output_modalities`，但一次只能一种（PC-B §4）；Ultravox：会话中 `set_output_medium` 切 voice / text（PC-B §4）；Step-Audio 2 mini：同一上下文，助手消息 `content: None` 只出文本、加 `<tts_start>` 出语音（HC Q1b）；LiveKit：每条消息检查，无 audio 模态且配了 TTS 就把文本 tee 给 TTS 和字幕（LK-B §4.1）。Pipecat 只用了全局设置（PC-B §4）；StepFun 可按回复带 modalities【推断】 |
| 适合谁 | 上游支持按回复选模态、又想保留 S2S 在场感的 A 类；只有一个上游、要在同一会话里区分高低风险回合的 B 类 |
| 坑 | ① **文本条目污染音频会话**：灌文本历史或文本回复后模型可能改用文本回复，LiveKit 为此专门报错（LK-B §4.2），trace 必须记 `reply_modality`；② 模态要在回复**开始前**选，内容没生成前只能按预测的回合类型选，音频模式下模型临时说起事实就无法审核；③ 截断方式随模态变（音频 `audio_ms`，文本 `text_rewrite`，04 §2.3）；④ Step-Audio 首轮加 `<tts_start>` 时可能先说一句再发工具调用【未确认】，原生语音模式能否按文本截停【未确认】（HC Q2、§3.1） |

### (b) 前台 S2S + 后台文本 LLM（委派）

```
用户音频 ──▶ 前台 S2S（上下文 #1）── 普通回合：直接出声
               │ 重回合：调用 delegate(intent_hint, last_utterance_gist)
               ▼
            后台文本 LLM（上下文 #2，只读工具 / RAG）── 流式正文
               ├ speak 通道 ──▶ 仲裁器 ─▶ 本地 TTS（或交回前台 commentary 由它自己说）
               ├ context 通道 ─▶ 状态块 / thinking，不出声
               └ terminal ────▶ 前台调用收口：回传"实际播出的文本"，不发再生成
```

| 项 | 内容 |
|---|---|
| 上下文份数 | **2**：前台 S2S 会话 + 后台 LLM 请求上下文（03 §6.1） |
| 声音 | 两种（前台原生声 + 本地 TTS）；走 commentary 让前台自己说可保持一种声音，但要付前台再生成 |
| 延迟：普通回合 | 0.87–0.96 s（实测，前台直出） |
| 延迟：工具回合 | 结果交回 S2S 再生成：2.6–3.5 s（推算，ORA §3.3），比现状 2.1 s（实测）更差；后台流式 + 本地 TTS：1.4–1.8 s；再加 ASR 定稿即投机起跑：1.0–1.3 s（均为推算，ORA §3.3；03 §3.1 A2）。短工具走委派：qwen bench 从说完到**工具开始执行**慢 +2.05 s（1.32 → 3.36 s，92 回合，仓库自述，不含回复音频，QW §3.1） |
| 智力来源 | **后台大文本 LLM**（任意模型、完整工具、RAG）；前台只决定"要不要委派"，这个判断的质量是短板 |
| 依赖的能力位 | 前台调用能静默收口（`tools.auto_reply_after_result = no` 或有 `flag`）；commentary / thinking 需要 `config.append_channels`（只有 GPT-Live，每条 ≤ 500 token，04 §2.2.3）；把后台事实补回前台要看 `history.mid_session_effective` |
| 代表实现 | Pipecat `OpenAILiveLLMService`：`ResponsesDelegation`（托管模型做后端）/ `ClientDelegation` + `BackendLLMWorker`（任意 LLM 做后端），按 `prefers_spoken` 走 commentary 或 thinking，委派失败 / 超时 / 无输出一定回一句（PC Q6）；qwen-audio-agent：委派确认一轮再生成，结果注入 user 条目又一轮再生成（QW §3.1）；openai-realtime-agents chat-supervisor：结果 → function output → `response.create` 再生成（ORA §3.1）；这里的协议是 03 §6（speak / context / terminal 三通道） |
| 适合谁 | S2S 为主、需要在场感又要长任务和复杂查询的 A 类 |
| 坑 | ① **延迟陷阱**：只要结果交回 S2S 再生成，就至少多付约 1.2 s，委派本身不省延迟（QW §3.4；BP A.1-2）；② **两份上下文**：前台不知道后台说了什么、后台不知道前台之后聊了什么，指代对不上（BP A2 风险）；③ 短的状态类工具不该委派（+2.05 s）；④ 前台可能在转写完成前就发出委派，要带 `last_utterance_gist`（ORA Q1）；⑤ 写操作不委派给后台模型，规则短路和门槛留在委派之前（03 §3.2 行 7）；⑥ 委派必须可取消，投机结果按代际作废（03 §6.3–6.4） |

### (c) 音频 LLM 出文本 + 文本层（+ 大文本 LLM 兜难题）+ TTS

```
松键 / 判停 ──▶ 整段音频 ──▶ 音频 LLM（只出文本；原生或提示词工具）
                                 │ 文本 / tool_call（工具调用先于任何音频上报，04 §6.3）
                                 ▼
                        文本层：出声前护栏 · 工具执行 · 路由
                                 │ 路由判为难题：调用 escalate → 大文本 LLM（读同一份文本历史）
                                 ▼
                        本地 TTS（唯一声音）──▶ 播放；已播文本写回历史
   并行：转写（流式 ASR，或回复后同模型低优先级转写）──▶ 历史里的本轮 user 文本
```

| 项 | 内容 |
|---|---|
| 上下文份数 | **1**：自己的 chat messages，历史一律存文本，只有本轮是音频（HC Q3；04 §6.2） |
| 声音 | **1**：全部走 TTS。与 (a) 叠加时（Step-Audio `<tts_start>` + `prompt_wav`）低风险回合可出原生语音 |
| 延迟：普通回合 | 未实测；仓库都没给 TTFT（HC §1）。构成 = 编码整段 + 预填充 + 首 token + TTS 首包；TTS 首包 CV2 单并发 P50 0.19–0.22 s（仓库自述，L20 + TRT-LLM），CV3 目标 ≤ 0.4 s（待测）。验收门槛：松键到首音 P50 ≤ 1.1 s（E2E-E2） |
| 延迟：工具回合 | 工具调用以文本出现、先于任何声音；续答由客户端发起，只付文本 TTFT，历史存文本时前缀可命中缓存。参照：Qwen3-Omni 一条"含工具定义 + 一段语音"的请求从预填充到输出两个 `<tool_call>` 约 0.56 s（仓库自述，单卡、型号未标，不是 TTFT，HC Q1a）。升级到大 LLM 时再加它的 TTFT（未实测） |
| 智力来源 | 音频 LLM 自身（Step-Audio 2 mini 推理弱，Big Bench Audio 54.8；Qwen3-Omni 30B-A3B 强，均仓库自述）+ 按路由升级的大文本 LLM |
| 依赖的能力位 | `output.modalities = text`；`tools.calling = native`（Step-Audio `step_audio_2` 解析器）或 `prompted`（Qwen3-Omni 手写 hermes `<tools>`）；`tools.auto_reply_after_result = no`；`uplink.streaming_input = whole_utterance`；`cascade.user_transcript = side_request`（04 §6.2–6.5） |
| 代表实现 | Step-Audio 2 mini（7B，24 GB 级单卡【推算】，代码与 mini 权重 Apache-2.0）；Qwen3-Omni Instruct + `disable_talker`（BF16 至少 68.74–78.85 GB，仓库自述）；ultravox（仓库无工具代码，E2E Q3）。云 S2S 固定只出文本（LK-B §4.1、PC-B §4）是它的"会话级"版本 |
| 适合谁 | 文本先于语音为主的 B 类（主链路）；A 类的长期升级项 |
| 坑 | ① **没有用户转写**（见下）；② demo 把历史原始音频留着（Qwen3-Omni 超 5 个音频回合删最早一轮），破坏前缀缓存，多模态前缀能否命中【未确认】；③ Step-Audio 用 stepfun 私有 vLLM 分支，角色名是方言（`human`、`input`、`tool_json_schemas`），标准 `role: tool` 能否接受【未确认】；④ mini 的工具准确率没有数字（评测只报闭源完整版）；⑤ 没有流式输入，开放麦要自己判停后整段提交；⑥ 失去原生表现力，只能靠 TTS instruct / 情感控制补 |

**另跑转写的代价与办法**。历史存文本需要本轮 user 文本，升级到大 LLM 更是当场就要。三种办法：

| 办法 | 时延影响 | 代价 |
|---|---|---|
| 说话期间并行跑流式 ASR（SenseVoice / FunASR） | 松键时基本已定稿，不加串行时延（上游 ASR 定稿约 0.37 s，实测，BP A.0） | 多部署一个模型；转写与音频 LLM "听到的"可能不一致，历史里的话和模型当时理解的不同 |
| 回复之后，同一模型发一次低优先级转写请求，结果以 `transcript.user.final{late: true}` 上报（04 §6.3） | 不在关键路径上 | 同卡抢算力；必须在下一回合开始前写回，否则下一轮历史缺一句 |
| 让模型先输出转写再回答 | 串行加在首音上 | 不推荐 |

升级到大 LLM 的回合要求当场有文本：用并行 ASR，或让音频 LLM 在 `escalate` 调用参数里带上"用户这句话的要点"（同 03 §6.1 的 gist 思路）。副语言信号（情绪、年龄段）若要跨回合保留，以短标注写进历史文本，不靠保留原始音频。

## 3. 三角平衡怎么算

### 3.1 按回合类型的评分表

评分为定性（高 / 中 / 低）；括号内是有依据的数字及口径。"纯 S2S""纯级联"作对照。

| 回合类型 | 纯 S2S | 纯级联 | (a) 按回复选模态 | (b) 前台 S2S + 后台 LLM | (c) 音频 LLM + 文本层 |
|---|---|---|---|---|---|
| **寒暄 / 安抚** | 速高（0.87–0.96 s 实测）· 智中 · 自然高 · 审低 | 速中（P50 1.4 s 实测）· 智中 · 自然中 · 审高 | 走音频 = 纯 S2S | 前台直出 = 纯 S2S | 速中（目标 ≤ 1.1 s，未测）· 智中 · 自然中（TTS 情感控制）· 审高；叠加 Step-Audio 原生语音时自然中高、审低 |
| **事实与方案** | 速高 · 智中 · 自然高 · **审低**（无文本窗口） | 速中 · 智按 LLM · 自然中 · 审高 | 走文本：速中（未测）· 智中（同一模型）· 自然中 · 审高 | 委派：速中（1.4–1.8 s，投机 1.0–1.3 s，推算）· **智高** · 自然中 · 审高（speak 通道逐句过护栏） | 速中 · 智中，升级大 LLM 后**智高**（多一次 TTFT，未测）· 自然中 · 审高 |
| **工具** | **速低**（有内容 2.1 s 实测）· 智中 · 自然高 · 审低 | 速中高（只付文本 TTFT，推算）· 智按 LLM · 自然中 · 审高 | 速中高（直念 ≈ 1.1 s 推算）· 智中 · 自然中 · 审高 | 同上行；短工具不委派（+2.05 s 仓库自述） | 速中高（续答只付文本 TTFT；0.56 s 参照，仓库自述）· 智中–高 · 自然中 · 审高 |
| **长讲解** | 速高 · 智中 · 自然**高** · 审低 | 速中 · 智按 LLM · 自然中（TTS 长文易平） · 审高 | 看风险：低风险走音频 | 后台长文本 + 本地 TTS；前台不被占住 · 智高 | 智中–高 · 自然中 · 审高 |

读法：**没有一列全是"高"**；最好的一行一行挑——寒暄选 S2S，事实选文本，工具选文本且不再生成。混合架构的价值就是把这张表按行取最优，前提是 §0 的四个前提让"换列"对用户无感。

### 3.2 为什么"普通回合 S2S 最快、工具回合文本路径反而更快"

- **普通回合**：S2S 一跳从音频到音频，没有 ASR 定稿尾巴，也没有独立的 TTS 首包；文本路径至少多一段 TTS 首包（0.2–0.4 s 量级，见 §2(c)）。所以 S2S 0.87–0.96 s 对级联 1.4 s（均实测）。
- **工具回合**：S2S 要先出 function call（约 0.8 s 实测），结果回传后**再做一次完整的音频生成**（约 1.2 s 实测）——重新读整段会话、再走一遍音频解码首包，合计 2.1 s。文本路径在这一步有三个优势：① 结果可以不经模型直接念（A1），整段再生成被删掉；② 需要组织语言时，只付文本 LLM 的 TTFT，而且历史是文本、前缀缓存稳定（KM 1.1、3.4）；③ 识别定稿即可投机起跑后台（03 §6.3）。所以工具回合是**结构上**文本更快，不是某个模型更快。
- 推论：混合架构里**工具回合一律由文本层组织、TTS 出声，S2S 只收口不再生成**（架构 §3.2 选路规则第 3 条）。这一条对 (a)(b)(c) 都成立。

## 4. 四个前提各自怎么达成

### 4.1 声音统一

按投入从小到大：

1. **TTS 克隆到接近 S2S 原生声**：从上游输出截 5–15 s 干净、中性的片段加准确转写作参考；风险是下行编解码失真被一起克隆、表演风格复现弱于音色、上游条款是否允许（TTS Q3）。零样本不够就用几十分钟语料 SFT（CosyVoice 有 recipe）。判定不看 SS 分数，看盲听"是不是同一个角色"（TTS-E2e，阈值建议 ≥ 80%，待定），并测短语间一致性（TTS-E2k）。
2. **S2S 也只出文本**：所有话走同一个 TTS，声音问题消失，代价是丢原生表现力（BP B.6-3）。用 TTS 的情感控制补一部分：CosyVoice instruct、IndexTTS 情感向量（KM 2.9；TTS-E2l）。
3. **Step-Audio 原生语音用自己的参考音**：token2wav 的 `prompt_wav` 换成目标声音，TTS 也用同一参考音，原生回合和 TTS 回合同源（HC Q1b；E2E-E8：MOS 差 ≤ 0.3 才算通过）。
- 通用要求：离线预合成的提示语与在线合成同模型、同说话人特征、同版本（KM 2.9）。做不到统一时，分流规则要把"声音切换"当成一种成本，减少高频切换（架构 §6-5）。

### 4.2 一份上下文

- **优先 (a) 和 (c)**：上下文本来就只有一份。(a) 要在 trace 里记 `reply_modality`，并防文本条目把会话"拉成文本"（P0-9）；(c) 要把历史存成文本（用户转写 + 助手已播文本），只保留本轮音频。
- **历史只记用户听到的**：助手文本按播放位置截断后写回（架构 §1 原则 2；文本模式下天然按 TTS 播放位置截断，PC-B §4）。
- **(b) 的指代问题与缓解**：
  - 前台 → 后台：委派请求带状态块、最近 K 轮（K 初值 4，建议值）且 assistant 部分用听到的文本、ASR 定稿或前台 gist（03 §6.1）；
  - 后台 → 前台：前台调用的 output 回传**实际播出的文本**（按播放位置截断），这是一条和调用配对的条目，比中途插入 user / system 条目可靠（中途插入实测"基本不看"，04 §2.2.2）；做不到就在空档以成对问答补记（ORA §3.2-5）；
  - 长期事实（名字、偏好、关键结果）走状态块，不指望任何一边的对话条目；
  - 验证：打断或长回答后问"你刚才说到哪了 / 刚才那个结果是什么"（QW E4）。

### 4.3 路由器

- **输入**：阶段（状态机当前阶段）、意图类别、工具注册表算出的路线 A0–A3（03 §3.2，按 `presentation`、`latency_class`、`write` 静态算出）、风险等级、上游能力位。
- **规则 + 小模型**：规则按"阶段 × 意图类别"给出默认路线；小模型（或流式 ASR 上的轻量分类器）只输出意图类别和置信度供规则查表。**不要引入串行时延**：阶段规则零成本；分类器与 ASR 并行，超时就回落到阶段默认；工具回合的路线由模型发出的工具调用触发，天然在出声之前（04 §6.3）。
- **规则即护栏，模型只提议**（架构 §6-2）：模型或分类器的提议只能把回合往"更可审核"的方向移（S2S → 文本），不能反向；高风险阶段禁用 S2S 直出和 A0（03 §3.3）；转人工、紧急出口由规则触发。
- **(c) 里的"升级到大 LLM"** 同样是提议 + 规则：音频 LLM 调 `escalate`（或路由按阶段直接升级），规则决定是否放行；写操作不随升级交给大模型执行。
- 路由决定、依据和回落原因都进 trace（`route_fallback_reason`，03 §3.3）。

### 4.4 上游能力位

| 能力位（04 §2） | 取值 | 处理 |
|---|---|---|
| 按回复选模态 `output.modality_switch` | `per_response` | 可做 (a) |
| | `per_session_live` | 能切但要改会话配置，按"切换代价"限制频率【推断】 |
| | `session_fixed` | 做不了 (a)；要么两个会话（即 (b)），要么整个会话只出文本（半级联） |
| 静默收口 `tools.silent_close` | `by_omission` / `flag` | A1 / A2 可用：结果本地念，只回传不再生成 |
| | `none` | A1 / A2 退到 A0（约 2.1 s）或改走半级联（03 §3.3） |
| 自动续答 `tools.auto_reply_after_result` | `no` | 默认形态；续答由本地发起，只在需要时付 TTFT |
| | `yes` | 省一次往返，但失去"本地直接念"；检查有无静默 flag；没有就把工具回合整体移出该上游 |

## 7. 反模式

1. **把结果交回 S2S 再生成**。委派、RAG、工具，只要最后一步是"function output → response.create → S2S 说"，就至少多付约 1.2 s；chat-supervisor 照搬推算 2.6–3.5 s，qwen 的委派一回合再生成两次（ORA §3.1、QW §3.1）。结果由文本层组织、TTS 出声，S2S 只收口。
2. **两份上下文各写各的**。前台不记后台说了什么、后台只拿自包含的 objective，或者双方都记"生成的全文"而不是"听到的文本"。结果是指代错乱、重复调用。要么选 (a)(c) 只留一份，要么按 §4.2 用委派请求、回传已播文本和状态块把两份对齐。
3. **S2S 与 TTS 两种声音**。不做克隆和盲听就上线混合，用户听到的是"两个角色轮流说话"，比统一走 TTS 更不自然。声音统一没过验收，就降低切换频率或全部走 TTS。
4. **路由交给模型自己判**。让 S2S 或音频 LLM 自己决定"这句要不要审核""要不要升级"，高风险内容会从没有审核窗口的路径出去。路由由规则（阶段 × 意图类别 × 工具路线 × 能力位）决定，模型只提议，且只能往更可审核的方向提议。
5. 附：**短工具也委派后台**（+2.05 s，仓库自述）；**为了"保留副语言"把原始音频留在历史里**（破坏前缀缓存，副语言应作为短标注写进文本历史）。
