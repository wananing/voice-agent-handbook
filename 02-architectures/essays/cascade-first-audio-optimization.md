## 0. 结论先行

1. **模型速度决定下限，架构决定实际离下限有多远。** 三个模型分别只贡献自己的首包（ASR 定稿、LLM 首 token、TTS 首块）。如果链路完全串行、每一段都等上一段"整件做完"，实际首音会比三个首包之和多出一到两秒：判停时的静音等待、ASR 尾巴、等整句、TTS 整句合成、建连、设备缓冲，这些都是架构造成的开销。按 §5 的推算，不换模型、只改架构，首音可以从约 3.6 s 降到约 1.1–1.4 s【推算】。
2. **五段串行模型**。首音 ≈ ① 判停 + ② ASR 定稿残余 + ③ LLM 首 token 加上首个可合成片段 + ④ TTS 首包 + ⑤ 下行与播放启动。优化手段只有三类：**重叠**（让后一段提前开始，与前一段并行，§1）、**压缩**（缩短某一段本身的等待，§2、§4）、**移出关键路径**（让某一段根本不在首音路径上，§3）。
3. **"有声音"和"有内容"是两个指标，分开计时**（KM 1.3、总结 §3.3、specs/06 §2.3）。提示语只能让"有声音"提前，不能冒充"有内容"。任何手段都要写明它改善的是哪一个；只改善"有声音"而让"有内容"变晚的（比如长提示语），属于 §6 里的反模式。
4. 计时口径沿用 specs/06 §2：开放麦从 T_ep（判停）算，按键从 T_rel（松键）算，离线对比从 T_ae（最后一个有声帧）算。分段字段用 `endpoint_ms`、`stt_final_at_ms`、`seg.llm_ms`、`seg.tts_start_ms`、`queue_wait_ms`、`sound_first_at_ms`、`content_first_at_ms`。unmute 的恒等式"首音 ≈ vad + llm + tts_start"（`notes/unmute` Q2e）可以用来检查报表是否自洽。

## 1. 重叠：让后一段提前开跑

### 1.1 抢先生成（preemptive / speculative generation）

- **做法**：判停还没最终确认时，就用当前转写启动 LLM（可选同时启动 TTS）。输出先扣在闸门里不播放。判停确认后，如果输入没有变化就直接放行；有变化就丢弃，用新输入重跑。
- **机制细节**：
  - **触发**：LiveKit 在 STT 产生 `PREFLIGHT_TRANSCRIPT` 时触发，或者在判停完成前产生了有变化的 `FINAL_TRANSCRIPT` 时触发。它的语义判停模型在 VAD 静音约 200 ms 时就预取一次预测。Pipecat 在 STT 预测"说完了"（eager end-of-turn）时触发。按键场景没有判停可以抢，等价的做法是在识别定稿时就起跑，不等后面的决策层（BP A2 的"投机起跑"：识别约 0.37 s 就定稿，不必等 0.8 s 的委派决定）。
  - **闸门**：LiveKit 用 `schedule_speech=False`，SpeechHandle 不入队；Pipecat 用 `SpeculationGate` 扣住输出，确认后放行。
  - **复用条件**（LiveKit，四项都满足才复用）：转写等价（按词比较，忽略大小写和标点）；回合结束钩子执行之后的上下文等价；工具表相同；`tool_choice` 相同。
  - **丢弃条件**：以上任何一项不满足；出现更新的转写（新的抢跑替换旧的）；用户说话超过 `max_speech_duration`（10 s）；单轮重试超过 `max_retries`（3 次）；打断；会话暂停或关闭；本轮决定不回复。
  - **为什么不抢跑工具**：工具有副作用，投机一旦被丢弃就无法撤销。LiveKit 的做法是工具执行放在授权之后，Pipecat 的做法是投机中一旦出现工具调用就撤销整次投机。结果是抢先生成只能加速普通回合，对工具回合没有帮助。"只读工具也抢跑"两家都没做。如果要做，前提是工具幂等、无副作用、结果带代际标记可以作废【推算】。
- **依据**：`notes/livekit-agents` Q4；`notes/pipecat` Q6；KM 1.3、2.7。
- **适用条件**：必须是级联，或者文本 LLM 在关键路径上（LiveKit 对 S2S 直接 return）。STT 要能给出稳定的 partial 或 preflight。上下文在回合结束钩子里的修改要可预测，状态块频繁变化会让"上下文等价"一直不成立。
- **代价与风险**：会有被丢弃的 LLM 调用，开启 `preemptive_tts` 时还要加上被丢弃的 TTS。转写被 ASR 二遍纠错改动时命中率会下降。如果闸门没有接到代际或仲裁器，被丢弃的输出可能漏播，所以必须和输出仲裁的代际机制一起做（BP A2 风险项）。
- **参数起点**：默认只抢跑 LLM，TTS 抢跑等 LLM 命中率稳定后再开。命中率门槛沿用 A-E4 的 ≥ 70%，浪费率（被丢弃的调用 / 总调用）先按 ≤ 30% 监控【推算】。开放麦下，VAD 静音 200 ms 触发一次，之后转写每变化一次替换一次。
- **预期收益**：命中时，LLM 首 token 与判停等待、ASR 尾巴重叠，关键路径上的 ③ 缩短 min(触发点到判停确认的间隔, LLM TTFT)。以 VAD 200 ms 触发、判停在 0.35–0.5 s 确认计，开放麦可省 0.15–0.3 s；触发得越早（preflight partial）省得越多【推算】。BP A2 估算投机能让有内容首音从 1.4–1.8 s 降到 1.0–1.3 s【推算】。

### 1.2 TTS 建连、预热、说话人缓存与 LLM 首 token 并行

- **做法**：发出 LLM 请求的同时，在后台建立 TTS 连接或会话，拿到第一个可合成片段时再等待连接就绪。本地 TTS 没有连接要建，等价做法是服务常驻并预热，启动时就把说话人特征算好缓存。云 TTS 用长连接复用，并提前刷新 token。ASR 也同样处理：按下键或唤醒时就建连，再补发预录的音频帧。
- **机制细节**：
  - unmute 的 `start_up_tts()` 只把建连任务挂上去，紧接着就发 LLM 请求，拿到首词时才 `await`，建连失败时指数退避重试。
  - CosyVoice 用 `add_zero_shot_spk` 加 `save_spkinfo` 缓存说话人特征。
  - 小智的火山双流式默认常驻长连接；阿里在 10 s 内复用连接，token 过期前 60 s 自动刷新；百炼在 60 s 内复用。
  - 小智 ASR 在按下键后的第一帧就建连，建连后补发最近 10 帧（约 600 ms）。
- **依据**：`notes/unmute` Q2d；`notes/tts-zh` Q2 第 3 条；`notes/xiaozhi-model-choices` §3.1、§3.2。
- **适用条件**：TTS 或 ASR 是远程服务，或者本地模型有冷启动开销。
- **代价与风险**：
  - 长连接空闲时仍占厂商并发配额（小智配置注释里写明了）。
  - "不等会话已开始就发文本"时，首段文本会不会丢未确认。
  - 补发预录帧时可能重复发一帧，握手超过约 600 ms 会丢开头【推算】。
  - 预热请求本身会触发 CosyVoice 本地流式的 `token_hop_len` 疑似 bug：第一次请求之后，首块要攒约 4 s 音频才出【推算】。自己封装时必须改成局部变量（TTS-E2b）。
- **参数起点**：连接复用窗口取 10–60 s；token 提前 60 s 刷新；预录补发 600 ms；说话人缓存在启动时生成，并和模型版本一起纳入版本管理。
- **预期收益**：握手和 TLS 从关键路径上移除，云服务一般可省 0.1–0.3 s【推算】。CosyVoice2 开说话人缓存后，首块 P50 从 218 ms 降到 185 ms【仓库自述】。

### 1.3 LLM 流式 → 句级切分 → TTS 流式

- **做法**：LLM 边输出，切分器边切出短语，每个短语立刻送 TTS 流式合成。前一句播放时后一句已经在合成。首句要尽量短，让第一个可合成片段尽早出现。
- **机制细节（切分规则）**：
  - **首段**：遇到 `。！？；，、` 并且累计 ≥ 6 字就切；累计到 12–15 字还没遇到标点，就在最近的标点或词边界强制切。目标是首段对应约 1–2 s 语音。
  - **后续段**：按 `。！？；` 切，每段 20–40 字；逗号只在超过 40 字时才用来切。
  - 小智的做法更简单：首句遇到逗号、顿号或 `~` 就切，后续只在句号类标点处切。
  - CosyVoice 内置的切句按 60–80 字一段、不在逗号处切，这是为离线音质设计的，**实时场景下必须自己切**。
  - **中文不能按空格切**：unmute 按空白切词，对中文会把整段回复憋到流结束才送出去。
- **逐词送的前提**：只有 TTS 本身支持文本流入时，逐词送才成立，比如 Kyutai TTS，以及火山、阿里、百炼、讯飞这类云端双流式 TTS（由服务端切句，本地的首句切分不再起作用）。CosyVoice 的文本流入（bistream）不能配 vLLM，也不做文本规范化；参考音频约 5 s 时，要先攒 30–40 个汉字才开始出声【推算】，所以只作对照组。
- **依据**：`notes/tts-zh` Q2；`notes/xiaozhi` §2.4；`notes/xiaozhi-model-choices` §3.1；`notes/unmute` Q2c；KM 2.9。
- **适用条件**：所有级联链路都适用。
- **代价与风险**：
  - 首段太短，韵律会断，句间还要重复 prefill 参考音频。分段文本短于参考文本的一半时 CosyVoice 会告警，所以参考文本选 10 字左右。
  - 文本规范化和 Markdown 清理要在切分之前做（CosyVoice 在文本流入模式下，以及文本里含 `<|…|>` 标签时，会跳过规范化）。
  - 如果 LLM 把回复写在工具参数的 JSON 里（小智的 `direct_answer`），要做增量解析，并留 5 个字符的安全缓冲，防止把 JSON 的闭合符号念出来。
- **参数起点**：首段 ≥ 6 字、在 12–15 字强制切；后续每段 20–40 字。在 TTS-E2c 上扫"首段 ≥ 6 字 / ≥ 12 字 / 逐字 / 整句"四组。
- **预期收益**：③ 从"等整句"（20–40 字，按流式速度约 0.4–0.8 s）缩短到"等首短语"（6 字，约 0.1 s）；④ 从整句合成时间缩短到首块时间【推算】。

## 2. 压缩判停段

### 2.1 VAD 静音 + 语义判停 + 短 / 长两档等待 + 自适应

- **做法**：VAD 检测到静音约 200 ms 时，跑一次语义判停模型。判"说完了"就只等一个短的 min_delay；判"没说完"就把等待换成 max_delay。用户在等待期间重新开口，等待作废。再按同一用户历史的停顿习惯，自适应地抬高 min_delay。
- **机制细节**：
  - smart-turn v3.2 输入最后 8 s 音频，模型 8 MB int8，CPU 上几十毫秒；判"没说完"后最多再等 3 s（`stop_secs`）。
  - LiveKit 默认 min_delay / max_delay 为 0.5 / 3.0 s，接流式检测器时是 0.3 / 2.5 s；中文阈值 0.355。
  - LiveKit 的 `DynamicEndpointing` 用指数滑动平均学习两类停顿：用户两段话之间的停顿，以及系统刚判完停就被用户打断时的停顿，据此把 min_delay 往上抬，上限是 max_delay。
  - unmute 用 STT 自带的停顿概率判停，阈值 0.6，前约 1 s 的预测丢弃不用。
- **依据**：`notes/turn-detection-vad` Q2；KM 2.3、2.4；两类架构 §3.3。
- **适用条件**：开放麦。
- **代价与风险**：
  - 判早了会截断用户，而且截断的代价比多等几百毫秒大。
  - 基于文本的判停（如 TEN Turn Detection）依赖识别文本，识别错字多时会被带偏。
  - 语义模型没有中文或特定人群（儿童、口音、噪声）的公开评测。
  - 停顿多的用户会频繁触发 max_delay。
- **参数起点**：VAD 最短静音 200–250 ms；min_delay 0.3 s；max_delay 2.5 s；判停段预算 0.3–0.6 s，不超过 2.5 s（两类架构 §3.3）。
- **预期收益**：相比单纯静音超时（常见默认 0.55–1.0 s，FunASR 的 VAD 是 800 ms），说完的回合可以省 0.3–0.6 s【推算】。

### 2.2 延迟流 STT 的尾巴冲刷，以及关掉 ASR 自带端点

- **做法**：判停之后，不按实时速度等 STT 慢慢吐出最后几个字，而是主动发结束信号，或者一次性灌入零帧，让 STT 以快于实时的速度把尾巴挤出来。同时关掉 ASR 自带的端点检测，或把它设得很小，避免它和自己的判停叠加等待。
- **机制细节**：
  - Kyutai STT 的输出比音频晚约 0.48 s（6 帧）。unmute 在判停后一次性灌入约 0.5 s 加一帧余量的零帧，STT 时钟越过冲刷点就立即生成回复。
  - FunASR 发 `is_speaking:false` 就会自动冲出尾巴，不需要灌零帧。
  - sherpa-onnx 流式要自己补 0.3–0.8 s 尾部静音。
  - ASR 服务自带的端点默认值往往很大：FunASR VAD 800 ms、阿里 `max_sentence_silence` 800 ms。小智按键模式下的讯飞 `eos` 直接设成 60 s，把收尾交给松键决定。
- **依据**：`notes/unmute` Q2b；`notes/asr-zh` Q1、§3.1；`notes/xiaozhi-model-choices` §3.2。
- **适用条件**：流式 ASR，包括延迟流模型和带内置端点的云 ASR。
- **代价与风险**：零帧灌入的实际耗时仓库没有数据。补的尾部静音太短会吞掉最后一个字。关掉 ASR 端点以后，切段完全靠自己的判停。
- **参数起点**：零帧长度 = ASR 延迟 + 1 帧；尾部静音在 0.3 / 0.5 / 0.8 s 三档上扫（ASR-E1b）；云 ASR 的端点参数取 200 / 400 / 800 ms 扫。
- **预期收益**：② 从"延迟 + 实时等待"缩短到"计算时间"，延迟流模型可省约 0.4 s【推算】。定稿目标 P50 ≤ 0.4 s（ASR-E1b，实践笔记里的上游约 0.37 s【实测】）。

### 2.3 按键场景：判停段归零

- **做法**：松键就是判停信号，① = 0。语义模型只做三件辅助的事：松键前压缩句中停顿、挡掉误触的短按、松键太早时留一个补充窗口。
- **机制细节**：
  - 本地 VAD 把超过 K 的静音帧丢掉，让上游看不到足够长的静音。约束是 K 加上恢复说话时补发的静音，要小于上游的静音阈值。
  - 短按丢弃门槛：按键 < 250 ms 或语音 < 150 ms。
  - smart-turn 判"没说完"时，留 W = 600 ms 的补充窗口，期间再次按键就合并成同一轮。
- **依据**：KM 2.3、2.4；BP C1；两类架构 §2.2。
- **适用条件**：按键说话，包括 B 类的按住说话降级模式。
- **代价与风险**：
  - 补充窗口只在判"没说完"的回合生效，但这些回合的首音会晚 W。
  - 如果上游不支持清空输入缓冲，就要在本地先缓冲约 300 ms、确认有语音再转发，首包会晚约 300 ms。
  - ASR 的尾巴冲刷（②）仍然要做，不会因为按键而消失。
- **参数起点**：K = 250 ms；W = 600 ms，上限 1000 ms；smart-turn 阈值 τ = 0.5（BP C1）。
- **预期收益**：① ≈ 0。判"没说完"的轮次控制在 ≤ 15% 以内（C-X4），平均增量 ≤ 0.1 s【推算】。

### 2.4 开放麦下的取舍

- **核心张力**：min_delay 越短，首音越快，但截断率越高。**抢先生成（§1.1）能改变这个取舍**：LLM 在 VAD 静音 200 ms 时就起跑，判停等待和 LLM 首 token 并行进行，min_delay 在不超过 TTFT 的范围内几乎不增加首音。所以有了抢先生成，就可以把 min_delay 设得保守一些（0.4–0.5 s），换来更低的截断率【推算】。
- **不要用填充音掩盖判停等待**：判停期间用户可能还要继续说，此时出声会被当成抢话。判停段的延迟只能靠压缩和重叠来减少。
- **自适应优先于全局调参**：不同用户的停顿习惯差异很大，全局参数无论怎么调都会同时伤到一部分人。按用户用 EMA 调整（DynamicEndpointing）是唯一现成的机制。

## 3. 移出关键路径

### 3.1 预合成提示语与固定前缀

- **做法**：会话开始时，用同一音色批量预合成提示语、问候语和错误话术，裁掉首尾静音后按文本缓存。在"决定要做什么"的那一刻就播放。如果回复的开头是固定的（模板化结果的前缀），也预合成，之后本地 TTS 只合成可变的部分。
- **机制细节**：
  - 提示语不进模型，也不写进上下文。
  - 输出种类记为 `cue` 或 `filler`，只算"有声音"，不算"有内容"。
  - 短 cue 控制在 ≤ 300 ms。如果工具在 cue 开播前已经完成，就不播 cue。
  - 同一种提示语准备多种措辞，随机轮换。
- **依据**：总结 §3.3；specs/06 §2.3、§2.4 示例；两类架构 §2.3；BP A1、A-E2。
- **适用条件**：需要等待的回合（工具调用、慢决策）；A 类尤其需要，因为 A 类"沉默即故障"。
- **代价与风险**：
  - 长提示语会让正文排队等待：specs/06 的示例中，长 cue 让正文等了 540 ms，有内容被推迟到约 1.6 s。
  - 提示语和在线合成的语音必须用同一个模型、同一份说话人特征、同一个版本，否则听起来是两个声音。
- **参数起点**：cue ≤ 300 ms；有声音 ≤ 0.9 s（A 类，从松键算）。
- **预期收益**：有声音提前到 0.82–0.87 s，基本等于"识别完成 → 做出决策"的时间；结果排在提示语后的等待 P50 为 0、P90 为 0.2 s【实测，总结 §3.3】。这一手对"有内容"没有帮助。

### 3.2 LLM 前缀缓存：稳定前缀在前，易变状态块放在末尾

- **做法**：prompt 从前到后按变化频率从低到高排：系统提示 / 人设 → 工具表 → 固定的 few-shot → 历史（一律存成文本）→ 状态块 → 本轮用户输入。易变的东西（状态、时间、检索片段）一律放在尾部，不插到前缀里。
- **机制细节**：
  - 前缀缓存按 token 从头开始逐一匹配，前缀里任何一个 token 变化，它之后的部分全部失效，要重新预填。
  - unmute 把 instructions 放在 `chat_history[0]`，不能照搬。qwen-audio-agent 的注释明确写了"重发 instructions 等于换前缀"。
  - 历史里保留原始音频会破坏文本前缀缓存，所以历史一律存成文本。
- **依据**：KM 3.4、2.7；两类架构 §2.2；`specs/05` 状态块位置一行；`notes/half-cascade-open` 前缀缓存一节；总结 §5.4（实测数字见 KM 3.4）。
- **适用条件**：自托管的 vLLM / SGLang，或者支持前缀缓存的云 API。
- **代价与风险**：状态块放在尾部，模型对它的注意力可能和放在系统提示里不同，要用 L0 用例回归一遍。工具表按阶段裁剪也会改变前缀，所以要么把全量工具表放在前缀里、在工具层拒绝不该用的调用，要么把每个阶段的前缀都预热一遍。
- **参数起点**：每轮 trace 记录 `cached_input_tokens`，目标命中率 ≥ 80%【推算】。
- **预期收益**：S2S 上游的实测反例：每次更新会话配置都会重新预填，未命中缓存的输入变成 ×3.2，首音多 80–200 ms；如果每轮都更新，多 150–270 ms【实测】。级联下长 prompt 预填的节省量要实测（A-E9）。

### 3.3 常用回复缓存 + 后台刷新

- **做法**：由规则短路就能确定文本的回复（唤醒应答、问候、固定确认、错误话术），直接播放缓存好的音频，不经过 LLM 和 TTS。缓存在后台定期刷新（换措辞、换音色版本）。
- **机制细节**：
  - 小智的唤醒词直接播放本地 wav，后台每 10 s 以上随机刷新一次回复的 TTS 缓存。
  - 小智的 `intent_llm` 按"设备 + 文本"的 md5 缓存意图结果，这属于决策缓存。
- **依据**：`notes/xiaozhi` §2.4；KM 2.9。
- **适用条件**：文本不依赖模型生成的回合。
- **代价与风险**：回复会显得机械，需要多条措辞轮换。缓存和线上 TTS 版本不一致会导致音色漂移。决策缓存在上下文不同的情况下可能给出错误答案，只适合跟上下文无关的意图。
- **参数起点**：刷新间隔 ≥ 10 s；每类回复 3–5 条措辞。
- **预期收益**：命中的回合，②③④ 全部省掉，首音约等于 ① + ⑤【推算】。

### 3.4 决策与正文分离：小模型出动作，正文并行生成，首句先播

- **做法**：先用一个最小档位的模型（关思考、带前缀缓存）只输出动作枚举和槽位，不写正文。规则修正层按当前状态纠正它的动作。动作一确定，就并行启动正文生成（长回答交给更大的模型），正文首句一切出来就交给 TTS。对于能模板化开头的动作，可以先播预合成的固定前缀（§3.1），正文同时生成。
- **机制细节**：
  - 决策模型的输出短、结构化，首 token 接近它的全部耗时。
  - 正文生成器拿到的是已经确定的动作，不需要再做一次意图判断，prompt 可以更短、更专。
  - 把写操作门槛和规则修正层放在"动作"和"正文"之间，执行权在 agent 侧，不在模型手里。
  - 进阶做法：动作分布高度集中时，可以在决策的同时投机启动最可能那个动作的正文，决策不一致就作废，道理同 §1.1【推算，未实现】。
- **依据**：总结 §3.1、§3.3；KM 2.7。
- **适用条件**：动作集合有限、需要可审核或需要规则兜底的场景（B 类高风险回合尤其适合）。
- **代价与风险**：动作和正文要走两次模型调用，决策段多出一个首 token 的时间。正文模型看不到决策模型的推理过程，要把动作和槽位完整传过去。
- **参数起点**：决策模型用最小档位、关思考，输出限制在几十个 token 以内。
- **预期收益**：策略层首 token 约 0.5 s；有声音和有内容几乎同时达成，P50 1.4 s【实测，总结 §3.1、§3.3】。对照：同一项目的 S2S 工具回合有内容 P50 为 2.1 s【实测】。

### 3.5 模型侧：关思考、短 prompt、合适的 max_tokens、小模型

- **做法**：
  - 关闭思考模式：小智按域名自动下发 `enable_thinking: False` 或 `thinking.type: disabled`，并剥掉流式输出里的 `<think>`；qwen3 在 Ollama 下给用户消息加 `/no_think`。
  - prompt 压短：去掉示例冗余；工具 schema 按阶段收窄；事实走通道，不写进人设。
  - 用 max_tokens 和"一两句话"的 prompt 约定控制回复长度。
  - 决策层用小模型。
- **依据**：`notes/xiaozhi-model-choices` §1.3、§4.1、§4.2；KM 2.7。
- **适用条件**：所有级联。
- **代价与风险**：
  - 关思考后，复杂推理的质量可能下降，这类回合交给后台模型处理。
  - max_tokens 主要影响回复总长和 TTS 的排队，对 TTFT 影响不大。它设得太小会把句子截断在半中间，要配合 prompt 约定使用，不能只靠它硬截。
  - 小模型的工具命中率要在盲测集上验证：小文本 LLM 选工具的命中率是 84%，P50 0.84 s【实测】。
- **参数起点**：思考默认关；max_tokens 取 200–500（小智 qwen-flash 配的是 500【仓库自述】）。prompt 长度作为 trace 维度记录下来，和 TTFT 一起做回归（A-E9）。
- **预期收益**：小智社区报告，约 6k 字角色 prompt、不带工具、并发请求时，首 token 为：qwen3-8b 0.59 s，qwen-flash 0.67 s，glm-4-flash 1.11 s，MiniMax-M2.7 3.43 s【仓库自述，口径粗】。模型之间的差异可达数秒，思考模式是最常见的原因之一【推算】。

### 3.6 旁路任务异步化

- **做法**：情绪识别、声纹、记忆写入、标题生成、上下文源拉取这些任务，一律不阻塞主链，结果晚到就留给下一轮使用。
- **依据**：小智的反例：声纹和 ASR 用 `gather` 并行，声纹接口超时 10 s，声纹一慢就拖住整轮；上下文源在构建 prompt 时同步 `httpx.get(timeout=3)`，首轮最多多等 3 s。小智做对了的：情绪识别异步；记忆保存放后台线程（`notes/xiaozhi-model-choices` §3.3；`notes/xiaozhi` §2.4）。
- **代价**：旁路结果至少晚一轮才能生效。
- **参数起点**：关键路径上的任何外部调用都设不超过 200 ms 的超时，并有降级值【推算】。
- **预期收益**：去掉长尾，主要改善 P90 / P99。

## 6. 反模式清单

| 反模式 | 为什么不行 | 改法 |
|---|---|---|
| 把判停期间的静音当成卡顿，用填充音盖住 | 用户可能还没说完，出声就是抢话；填充音也会被自己的 VAD 或上游误当成人声 | 判停段只靠压缩和重叠缩短（§2.4）；填充只用在"已判停、在等工具或决策"的阶段 |
| TTS 整句合成完再发 | 首音多出整句合成时间，而且句与句之间串行（小智非流式 provider 就是这样，第 N+1 句要等第 N 句合成完） | 流式首块立即下发；后一句在前一句播放时就开始合成（§1.3） |
| 结果排在提示语后面串行等待，或者等提示语播完才去拿结果 | 提示语的时长整段串进有内容的延迟（A-E7 要量化这一项；LiveKit 的 S2S 路径要等排队的话播完才回传结果） | 结果立即产出、立即就绪，只在播放时排在提示语后面；用短 cue，工具已完成就不播（§3.1） |
| 易变内容放在 prompt 前缀（时间、状态、检索片段放进系统提示，或者每轮改 instructions） | 前缀缓存从变化点往后全部失效，每轮都重新预填（S2S 上实测未命中缓存的输入 ×3.2） | 按变化频率排序，易变的放尾部（§3.2） |
| prompt 太长（人设写事实、全量示例、全量工具 schema） | TTFT 随预填长度增长，缓存不命中时尤其明显 | 事实走通道；工具按阶段收窄；示例精简（§3.5） |
| 中文照搬按空格逐词送 TTS | 整段回复被憋到流结束才送出 | 按标点和字数切（§1.3） |
| 默认开着思考模式 | 首 token 被思考过程拖慢，可能慢几秒 | 按厂商参数显式关闭，并剥掉 `<think>`（§3.5） |
| 关键路径上同步调外部服务（声纹、上下文源、记忆） | 长尾超时直接变成首音延迟 | 异步化，设短超时和降级值（§3.6） |
| ASR 自带端点和自己的判停叠加 | 两层静音等待累加，比如 800 ms 加上 min_delay | 关掉或调小 ASR 端点（§2.2） |
| 抢先生成连工具一起抢跑 | 副作用无法撤销 | 遇到工具调用就撤销投机，或只允许幂等的只读工具（§1.1） |
| 一次性推送大段音频、设备深缓冲 | 打断时要 flush 几秒，播放位置不可知 | 服务端限速，超前 200–500 ms（§4） |
| 只报一个"首音"数字 | 提示语会把"有声音"做得很好看，掩盖"有内容"慢的问题 | 两个指标分开报，并注明锚点（§0） |

## 7. 与两类架构的关系

**A 类（无界面硬件；主链路是 S2S，级联只用在工具回合、逐字念和后台正文）**。优先顺序：

1. §3.1 预合成短 cue 加固定前缀。沉默即故障，"有声音"最要紧，而且收益已经实测过。
2. §2.3 按键归零判停，加 §2.2 ASR 尾巴冲刷。
3. §1.1 抢先生成用在"识别定稿即投机起跑"的后台正文上（BP A2）。
4. §1.2 本地 TTS 常驻、预热和说话人缓存，同时修掉 hop bug。
5. §4 设备协议：限速、浅缓冲、首包即播、分句下发。它和 A-E6 的播放回执一起落地。
6. 开放麦阶段再引入 §2.1 语义判停和 §2.4 自适应等待。

**B 类（有界面移动端、开放麦；高风险回合走级联）**。优先顺序：

1. §2.1 判停和 §1.1 抢先生成一起做。B 类从判停开始算，① 和 ③ 的重叠是收益最大的一项。
2. §1.3 首短语切分加流式 TTS，以及 §1.2 并行建连。
3. §3.4 决策与正文分离。高风险回合的出声前护栏正好放在"动作"和"正文"之间，首句先播。
4. §3.2 前缀缓存布局加 §3.5 模型侧手段。
5. "有声音"可以先由屏幕状态兜住，但两类架构 §3.3 要求语音"有声音"≤ 1.0 s。填充句只在工具回合使用。
6. §4 在 WebRTC（libwebrtc 两端）下大部分由媒体栈提供；自研 WebSocket 时照 A 类补齐。
