# 半级联：实时模型出文本，自己 TTS 出声

> 状态：草稿
> 最后更新：2026-10-01

**要点**：半级联让一个能直接"听"音频的模型（云端实时模型设成只出文本，或自托管的音频 LLM）负责理解和决策，**只产出文本**；出声交给自己的 TTS。它省掉了级联里独立的 ASR 一跳，又保留了级联最重要的性质：**文本先于语音**。换来的是声音统一、逐字可控、"自己的话"可以本地合成，以及判停、上下文、历史长度重新回到自己手里；代价是多一段 TTS 首包、失去模型原生的语音表现力，还要另外解决"用户说了什么"的转写。

---

## 1. 这种形态是什么

```
 用户音频（判停后整段，或实时流）
        │
        ▼
 ┌────────────────────────────┐
 │ 音频理解模型（只出文本）    │   来源 A：云端 S2S 设成文本模态
 │  · 理解 + 决策 + 工具调用   │   来源 B：自托管音频 LLM（Thinker / 音频编码器 + 文本 LLM）
 └─────────────┬──────────────┘
               │ 文本 / tool_call（先于任何声音出现）
               ▼
 ┌────────────────────────────┐
 │ 文本层（自己的代码）        │   出声前护栏 · 工具执行 · 路由（难题升级到大文本 LLM）
 └─────────────┬──────────────┘
               │ 要说的文本（模型的话 + "自己的话"）
               ▼
         自己的 TTS（唯一的声音）──► 下行 ──► 播放
               │
               └─► 已播放文本写回历史
   并行（可选）：流式 ASR ──► 本轮用户转写，进文本历史
```

和级联比，它只差三点（其余的判停、上下文、截断、护栏、声音都一样）：

1. **省掉 STT 一跳**：音频直接进理解模型。省下的是 ASR 定稿的尾巴，多出的是编码器处理整段音频的时间。
2. **可能保留一部分副语言**：语气、情绪、年龄这些 ASR 会丢掉的信息，模型有机会听到。但是否真的保留取决于训练目标（见第 4 节）。
3. **没有用户转写**：理解模型不产出 user 文本，历史要存文本就得另跑转写。

和 S2S 比，它放弃了"模型直接出声"，换回了"出声之前有一段完整文本"。

## 2. 为什么要这么做

| 动机 | 解释 |
|---|---|
| **声音统一** | 所有话都走同一个 TTS：模型的回复、工具结果、到点播报、兜底话、提示语，用户听到的是同一个角色。混用 S2S 原生声音和本地 TTS 时，"两个人轮流说话"本身就是最大的不自然 |
| **逐字可控** | 位置、时间、数字这类关键事实可以由我们写好文本、原样念出，不经过模型改写。S2S 里"逐字念"要依赖上游提供专门事件，且未必逐字 |
| **出声前审核** | 整句文本在 TTS 之前，护栏有完整的检查窗口。S2S 的文本只比音频早几十毫秒，护栏只能事后纠偏 |
| **"自己的话"本地合成** | 打卡结果、事件播报、识别失败兜底这类"我们的话"，本来就该本地合成、本地播放。在半级联里它们和模型的话走同一条 TTS，不需要单独的声音处理 |
| **控制点收回** | S2S 链路上受制于上游的六件事：判停、上下文注入、缓存、轮数上限、错误恢复、声音统一。在半级联里都变成自己的代码（上下文就是 chat messages，请求无状态，重试即恢复） |
| **工具回合更快** | 工具调用以文本出现、先于任何声音；续答只付文本 TTFT，不付"回传后再生成一段音频"的约 1.2 s（S2S 的实测量级） |

一份实践笔记的经验可以作为参照：它的 S2S 链路里，"我们的话"（打卡结果、到点播报、兜底）已经改成用同一音色本地合成、设备本地播放，播完再以成对问答补记进上游上下文。半级联把这个做法推广到了**所有**输出。

## 3. 适合与不适合

**适合**

- 需要出声前审核、事实必须准确的场景，同时又想省掉独立 ASR 或利用模型的音频理解。
- 输出里"自己的话"占比高（事件播报、固定话术、工具结果直念多）的产品，声音统一的收益大。
- 按键说话的设备：松键时整段音频已经齐了，正好对应开源音频 LLM"整段提交"的接口。
- 已经在用 S2S、但被上游会话语义卡住（判停关不掉、上下文注入不生效、20 轮墙），想把控制点收回来的团队。

**不适合**

- 闲聊陪伴、强调语气和在场感的产品：TTS 补不回 S2S 的原生表现力。
- 普通回合首音预算极紧（目标在 S2S 的 0.9 s 量级）的场景：多出来的 TTS 首包很难抹平。
- 资源受限、不想自托管大模型的团队：开源理解端要么推理弱，要么要 80 GB 卡（见第 4 节）。

## 4. 两类理解端

| 来源 | 做法 | 依据 |
|---|---|---|
| **云端 S2S 设成只出文本** | OpenAI Realtime `output_modalities=["text"]` 后接 TTS；Ultravox 会话中 `set_output_medium` 在 voice 和 text 之间切；Gemini Live 设 TEXT 模态会打警告"可能不被新模型支持" | Pipecat `examples/realtime/realtime-openai-text.py`、`realtime-ultravox-text.py`；LiveKit `RealtimeModel(modalities=["text"])`，框架在消息没有 audio 模态且配了 TTS 时把文本 tee 给 TTS 和字幕（`voice/agent_activity.py`） |
| **自托管音频 LLM** | Step-Audio 2 mini（7B，单个 LLM 交错输出文本与音频 token，不加 `<tts_start>` 就只出文本，vLLM 分支有原生工具解析器）；Qwen3-Omni（30B-A3B MoE，`disable_talker()` 或 `return_audio=False` 只用 Thinker）；ultravox（Whisper 编码器 → 投影 → 文本 LLM，天然只出文本） | 各仓库 README 与示例 |

开源理解端的现状（仓库自述或读代码得出，均未实测）：

| | Step-Audio 2 mini | Qwen3-Omni（只用 Thinker） | ultravox |
|---|---|---|---|
| 体量 / 显存 | 7B，24 GB 级单卡大概率够（推算） | BF16 最低约 69–79 GB（仓库自述），去掉 Talker 省约 10 GB | 8B 版约 16 GB（推算） |
| 流式输入 | 无，整段输入 | 无，整段输入 | 无（块因果只在实验配置） |
| 工具调用 | 原生：OpenAI `tools` + `step_audio_2` 解析器 + 回注续答示例 | 靠系统提示里手写 `<tools>` 格式，只有单次触发示例 | 仓库里没有工具代码 |
| 副语言 | 有公开评测（自家评测集，mini 平均 80，情绪 82，年龄 94） | 只有定性示例 | 训练目标是 KL 蒸馏"表现得像读了转写稿"，副语言没有训练目标支撑 |
| 推理能力 | 弱（Big Bench Audio 54.8） | 强 | 取决于底座 |
| TTFT | 仓库无数字 | 仓库无 TTFT；一条"工具定义 + 一段语音"请求从预填充到输出两个 tool_call 约 0.56 s（单卡、型号未标） | 仓库无数字 |
| 部署 | 要用 stepfun 的 vLLM 分支 | 官方 vLLM；`vllm serve` 只跑 Thinker | 官方 vLLM |

## 5. 关键取舍

| 维度 | 半级联的表现 | 说明 |
|---|---|---|
| 普通回合延迟 | 中 | 编码整段 + 预填充 + 首 token + **TTS 首包**。TTS 首包是多出来的一段：CosyVoice2 单并发 P50 0.19–0.22 s（仓库自述，L20 + TRT-LLM），一般按 0.2–0.4 s 量级估。一个可用的验收门槛是松键到首音 P50 ≤ 1.1 s（建议值，未实测） |
| 工具回合延迟 | 中偏快 | 工具调用以文本出现，续答由客户端发起，只付文本 TTFT；历史存文本时前缀可命中缓存 |
| 可控性 | 最高 | 文本先于语音；判停、上下文、历史长度、错误恢复全自控 |
| 自然度 | 中 | 失去原生表现力，只能靠 TTS 的情感控制（instruct、情感向量）补 |
| 成本 | 理解端 + TTS | 自托管时理解端是大头；云端文本模态按实时模型计费（各家定价待确认） |
| 对上游的依赖 | 低（自托管）/ 中（云端文本模态） | 云端文本模态仍受该上游的会话语义约束，只是去掉了"声音"这一层 |

### 5.1 "没有用户转写"怎么办

历史存文本需要本轮 user 文本；升级到大文本 LLM 的回合更是当场就要。三种办法：

| 办法 | 首音影响 | 代价 |
|---|---|---|
| 说话期间并行跑流式 ASR | 松键时基本已定稿，不加串行时延 | 多部署一个模型；转写和理解模型"听到的"可能不一致 |
| 回复之后同一模型低优先级转写一次 | 不在关键路径 | 同卡抢算力；必须在下一回合开始前写回 |
| 让模型先输出转写再回答 | 串行加在首音上 | 不推荐 |

副语言信号（情绪、年龄段）若要跨回合保留，以短标注写进文本历史，不要靠保留原始音频——开源 demo 把历史原始音频留着（Qwen3-Omni 的 web demo 最多保留 5 个音频回合），会破坏前缀缓存。

### 5.2 混合：按回合分流

半级联常常作为混合架构的一条腿出现：**每个回合按类型和风险选一条路**，寒暄走 S2S（快、自然），事实、方案、工具走半级联或级联（可审核、工具回合快）。一份设计讨论给出了三种混合形态：

| 形态 | 做法 | 上下文份数 | 主要风险 |
|---|---|---|---|
| (a) 同一上游按回复选模态 | 低风险回合要音频，高风险回合要文本 + 本地 TTS | 1 | 文本条目可能把音频会话"拉成文本"；模态要在回复开始前就选 |
| (b) 前台 S2S + 后台文本 LLM | 前台负责在场，重回合委派给后台，结果走本地 TTS | 2 | 两份上下文对不齐；结果交回 S2S 再生成会多付约 1.2 s |
| (c) 音频 LLM 出文本 + 文本层 + TTS | 就是本页的形态，难题升级到大文本 LLM | 1 | 理解端能力和转写问题 |

混合成立的四个前提，缺一不可：**声音统一**（S2S 原生声与 TTS 声听不出是两个人，或者全部走 TTS）、**一份上下文**（无论走哪条路，下一回合看到的都是用户实际听到的同一份历史）、**规则路由**（模型只能提议，且只能往"更可审核"的方向提议）、**上游能力已确认**（按回复选模态、静默收口等能力用探针测过）。这是一种实践的结论，不是业界共识。调研过的框架里，OpenAI Realtime 协议允许每次 `response.create` 选模态，但 Pipecat 只用了全局设置，也没有 S2S 与级联之间按回合切换的实现；其他框架是否有待确认。

## 7. 涉及的机制

| 机制 | 半级联里的关注点 |
|---|---|
| [turn-detection](../03-mechanisms/turn-detection.md) | 判停完全自控；开源理解端没有流式输入，开放麦要先判停再整段提交 |
| [first-audio](../03-mechanisms/first-audio.md) | TTS 首包是新增的一段，首句切分和 TTS 预热更重要 |
| [tool-calls](../03-mechanisms/tool-calls.md) | 工具调用先于声音；结果可直接念 |
| [interruption](../03-mechanisms/interruption.md) | 截断按 TTS 播放位置做，与级联相同 |
| [session-recovery](../03-mechanisms/session-recovery.md) | 请求无状态，恢复只需重拼消息 |
| [evaluation](../03-mechanisms/evaluation.md) | 理解端要和"ASR + 同底座 LLM"在同一批样本上比 |

## 待确认

- 开源理解端（Step-Audio 2 mini、Qwen3-Omni）的 TTFT 与端到端首音，仓库都没有给数字。
- 多模态前缀缓存能否命中（历史含原始音频 vs 只含文本）。
- Step-Audio 2 的 vLLM 分支能否接受标准 `role: tool`；首轮加 `<tts_start>` 时是否会先说一句再发工具调用。
- Qwen3-Omni 权重的许可证（仓库里没写）、`vllm serve` 是否支持流式输出。
- 理解端在儿童语音、户外噪声下是否不低于"ASR + 同底座 LLM"。
- 各家云端实时模型文本模态的计费方式。
