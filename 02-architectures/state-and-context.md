# 状态与上下文：放在哪、谁是真相

> 状态：草稿
> 最后更新：2026-10-02

**要点**：语音 agent 至少有四处地方"存着状态"：业务后端、agent 自己的本地上下文、上游模型的会话、断线用的快照。一种被几个项目趋同验证过的分工是：**写操作以业务后端为唯一真相**，agent 里的业务状态只是投影，可以随时丢弃重建；**agent 的本地上下文是对话的唯一真相**，上游会话只是它的镜像，只写不读；模型要选动作，就给它一个**结构固定、带版本的状态块**；上下文**只记用户实际听到的**；会话靠**快照**跨连接存活。在级联里这些大多是自然而然的；在 S2S 里每一条都要和上游的会话语义较劲。

---

## 1. 这个决策是什么

```
 ┌────────────────────── 业务后端（唯一真相：任务、打卡、订单）──────────────────────┐
 │  写操作只由后端判定成败；agent 通过工具层读写，带幂等键                              │
 └───────────────────────────────▲──────────────────────────────────────────────────┘
                                 │ 工具调用 / 读回
 ┌───────────────────────────────┴───── agent 本地上下文（对话的唯一真相）──────────┐
 │  对话记录（只追加；assistant 只记用户听到的）                                       │
 │  状态块（结构固定、带版本；只放自己的数据）  人设（分节、带版本）  工具表（固定）     │
 │  业务状态投影（行程、任务态：可丢弃，从后端重建）                                   │
 └──────────┬──────────────────────────────────────────────────────┬────────────────┘
            │ 投影：建会话时带历史；两轮之间更新状态块                  │ 每回合终态后写
            ▼                                                        ▼
  上游会话（S2S 的镜像，只写不读，            会话快照（如 Redis，TTL = 恢复窗口）
  随时可能失效、满了、要换）                  断线后在窗口内重连 = 同一会话
```

这个决策回答四个问题：业务状态以谁为准？对话历史以谁为准？模型怎么看到它需要的状态？断线之后什么能恢复？

---

## 2. 原则

### 2.1 后端是唯一真相

agent 内存里的行程、任务态都是后端状态的投影，任何时候可以丢弃、从后端重建。写操作只由后端判定成败：agent 发起，后端核验，结果分"成功 / 被拒 / 不可用"三类，只有成功才推进本地状态。一份实践笔记把"到点打卡"做成一条单独的任务线：到达信号先去抖，每个（实例，节点）一个稳定的 attempt id 让后端幂等，然后才由后端按节点配置核验。

好处是本地状态可以重放、快照、在测试里穷举（该笔记把行程做成"列表 + 游标"、所有操作都是纯函数）；坏处是每次写都要一次后端往返。

### 2.2 本地上下文是对话的唯一真相，上游是镜像

所有重建、摘要、快照、评测都从本地上下文出发。上游会话里的对话只是本地上下文在某一时刻的投影，**只写不读**：不能从镜像反推本地记录，也不能用镜像重放历史。原因是镜像不一定跟随截断：LiveKit 的 fallback adapter 重建会话时用的是"用户听到的"agent 上下文，而不是服务端镜像。

### 2.3 上下文只记用户实际听到的

助手条目在**播放回执到达后**才确定写进去的文本：播完 = 全文，被打断 = 按播放位置截取并带显式打断标记，没播出 = 不进。开源里的三种实现：

- **Pipecat 级联**：TTS 给每个词打 pts，按时钟释放，没到播放时刻的词进不了 assistant 聚合器。
- **unmute**：写进历史的是 TTS 按播放时刻回吐的词。但它在送 LLM 前去掉了打断标记（怕模型学着输出破折号），模型看不到"自己被打断了"，这一点不建议照搬。
- **LiveKit S2S**：打断时 `truncate(audio_end_ms)`，一帧没播出的消息从服务端删掉。

反例：小智服务端把已生成的全文写进历史，不截断也不标记；qwen-audio-agent 开始播放后被打断仍写入完整转写。

另外两条：提示语（cue）只进本地记录、**永不进模型上下文**；"自己的话"（本地合成的工具结果、事件播报）和模型的话同等进历史，让模型知道"自己说过"。

### 2.4 模型可见的状态块

模型负责选动作，就必须看得到选择所需的状态。一份实践的写法：

```
【现在的情况】
路线：已选「X 线」，进行中，已打卡 2 / 7
下一站：某高炉；之后还有 5 站
人在：秀池附近
限制：一个小时内
刚说到：三高炉          ← 只在重建会话时带，会话中靠对话本身
```

| 规则 | 说明 |
|---|---|
| 结构固定 | 字段和顺序由 schema 定义，空值写"无"而不是省略 |
| 带版本 | 结构版本 + 内容版本，写进每轮 trace，可以按版本分批比较效果 |
| 只放自己的数据 | 进度、用户选择、用户告知的硬信息（名字、陪同人）、当前阶段；**不放业务事实**，事实走通道（逐字念、RAG、上屏） |
| 有长度上限 | 该实践 ≤ 260 字 |
| 自然短句 | 不写 JSON，避免模型模仿格式说话（建议，未实测） |
| 只在两轮之间更新 | 回合进行中的变化排队；检查点是回合结束、下一次回合开始前 |
| 两层生效 | **立即生效**（不更新就会选错动作：选定路线、新建任务、特殊模式）和**懒生效**（进度计数、次要偏好），后者等下一次更新或重建时顺带带上 |
| 位置 | S2S 放系统提示末尾；自己拼消息的级联放**消息尾部**，保证前缀稳定、前缀缓存可命中 |

效果数据（该实践）：加状态块后多轮上下文用例从 66/80 升到 76/78，"开始吧"这一组从 8/16 升到 15/16——后者靠的是状态及时更新，所以不能为了省预填把所有字段都放懒生效层。

### 2.5 历史只在建会话时带入

在 S2S 上，该实践的接续对比是：建会话时带入成对问答 6/6；用会话 id 接续 1/6；建会话后逐条插入 0/6；中途插入 system / user 条目说明状态"基本不看"。所以历史走会话初始化参数，状态走系统提示，中途插入只允许几种情况（工具结果回传、按回复覆盖指令、协议专门的追加通道）。级联不受此约束：每轮自己拼消息，注入即生效。细节见 [s2s](s2s.md) 第 4.2 节和 [session-recovery](../03-mechanisms/session-recovery.md)。

### 2.6 会话快照跨连接

设备断线重连，在恢复窗口内（该实践 30 分钟）是同一个会话：

| 快照内容 | 恢复方式 |
|---|---|
| 业务状态投影、任务态 | 直接恢复（或从后端重建） |
| 状态块当前值与版本 | 写进新会话 |
| 最近若干轮对话记录（该实践 12 轮） | 用建会话参数带入 |
| 摘要及其覆盖范围 | 避免重新摘要 |
| 指代记忆（"刚说到的点"） | 写进状态块 |
| 在途工具调用、已执行写操作的幂等键 | 防止重放副作用 |

快照在每个回合终态后写一次，不含原始音频，不含上游镜像。用户主动"重新开始"是开新会话的唯一方式，可以分"只清对话"和"连业务状态一起清"两档。同一会话出现多条连接时，只有持有"前台租约"的连接能驱动上游和出声。

## 3. 长会话

上游通常只保留有限轮数（一个闭源上游上观察到约 20 轮），用户早期说的信息会丢。应对：

- **硬信息走状态块**，不依赖摘要或历史；摘要与状态块冲突时以状态块为准。
- **摘要在自己这层做**，用自己的文本 LLM，提前异步生成，等下一次重建时用；输入只用已播放文本、用户定稿文本和已收口的工具结果。
- **不对摘要再摘要**：新摘要从原始条目重新生成。
- **主动换会话**：按轮数、时长、状态变化在空档重建，用"摘要 + 最近几轮原样 + 状态块"初始化。让"会话丢了、满了、要换了"成为常规路径而不是故障路径。
- **工具表固定**：建会话时一次给全，会话中不改；按阶段限制在工具层拒绝并收口。

## 4. 适合与不适合

- **必须认真做**：S2S 链路（上下文注入受限）；断线频繁的移动设备和硬件；有写操作的业务（后端是真相、幂等）；长会话陪伴类产品。
- **可以从简**：纯级联、短会话、无写操作的原型。此时每轮把完整历史发给 LLM 就够了（unmute 就是这样做的，没有截断或摘要），代价是长会话会超出模型上下文。

## 5. 关键取舍

| 取舍 | 说明 |
|---|---|
| 状态块更新频率 vs 缓存 | S2S 每次更新会话配置，上游重新预填整段对话；该实践实测未命中缓存的输入 ×3.2，粗粒度更新首音 +80–200 ms，每轮更新 +150–270 ms |
| 状态块完整 vs 简短 | 越完整越不容易选错，越长越贵、越容易被模型当成要念的内容 |
| 本地真相 vs 依赖上游续接 | 自己存全量记录多写代码；依赖上游的会话 id 续接实测 1/6 |
| 摘要放哪 | 历史开头一对问答（有文本条目污染音频会话的风险）或并进系统提示（前缀随摘要变化） |
| 快照粒度 | 存得越多恢复越完整，写入越频繁；该实践每回合终态写一次 |

## 6. 开源项目怎么做

| 项目 | 做法 |
|---|---|
| [pipecat](../04-projects/frameworks/pipecat.md) | 级联按 TTS 时间戳写回助手消息；所有 S2S 服务会话中途只同步工具结果；`LLMContextSummarizer` 不切断未完成的工具调用；Nova 服务后台预建下一个会话、在空档交接 |
| [livekit-agents](../04-projects/frameworks/livekit-agents.md) | 打断时 truncate；`RealtimeCapabilities` 声明能否改历史 / 指令 / 工具；不可变上游只在建会话时带入历史；`_summarize` 用文本模型做摘要 |
| [unmute](../04-projects/full-duplex/unmute.md) | 上下文 = 已播放的词；每轮把完整历史发给 LLM，无截断、无摘要 |
| [qwen-audio-agent](../04-projects/frameworks/qwen-audio-agent.md) | 建会话后插入：收到 `session.updated`（上游不回执 `session.update` 时则是 `session.created` 后）由 `RealtimeFrontend.restoreRecentConversation` 把近期对话打包成一条 `<restored_context>` user 条目写入，写完才标记 ready（`server/src/voice/realtime-provider.mjs:completeSessionSetup`），属于上文"建会话后插入"一类，这种做法的效果仓库里没有评测数据；能力位 `restoreConversationContext`、`mutableSession`；任务状态的唯一权威在 `TaskManager` |
| [xiaozhi-esp32-server](../04-projects/devices/xiaozhi-esp32-server.md) | 一个连接一个会话，历史是无上限的 list；记忆（`mem_local_short`）在会话结束时用一次 LLM 压成档案，下次会话注入系统提示，会话内不更新 |

## 待确认

- 接续方式的对比每组只有 6 次、只测了"名字"一类回忆；往音频会话灌文本历史后是否会让模型改用纯文本回复，没有检查过。
- 按回复覆盖指令、追加通道（如 OpenAI Live 的 `instructions.append`）是否同样破坏缓存、是否真的生效。
- 被打断条目的显式标记用自然语言写（如"（说到这里被用户打断）"），模型是否会模仿，未验证。
- 摘要放在历史开头还是系统提示里效果更好。
- 状态块 260 字上限、快照 12 轮是一个项目的实践值，换场景需要重新校准。
