# 全双工：边听边说

> 状态：草稿
> 最后更新：2026-10-02

**要点**："全双工"这个词被用得很宽，至少指三种不同的东西：按键或判停后轮流说的**半双工**；说话时也在听、但只为了检测打断的**可打断的半双工**；以及双方的流同时进出、由模型每一帧决定说不说的**原生全双工**。大多数产品真正需要的是第二种，用流式组件组装出来；第三种以 moshi 为代表，体验最接近真人对话，但几乎没有可控面：没有判停事件、没有工具、出声前没有文本审核窗口。

---

## 1. 三种"双工"

```
 半双工（按键 / 判停后轮流）
   用户: ████████░░░░░░░░░░░░████████░░░░░░░░░░
   agent:░░░░░░░░░░████████░░░░░░░░░░░████████
         说话时不听；边界是按键或判停

 可打断的半双工（"组装式全双工"）
   用户: ████████░░░░░░░███░░░░░░░░░░░░░░░░░░░
   agent:░░░░░░░░░░████████✂ ░░░░░░████████░░░
         说话时一直在听（需要 AEC），听到用户开口就停；任一时刻仍只有一方"持有话筒"

 原生全双工（双流同时）
   用户: ████████░░░░░░███░░░░░░████░░░░░░░░░░
   agent:░░░░░░░██████████████░░░░███████████░
         两路音频同时进出，模型每 80 ms 决定这一帧说什么（可以是沉默、附和、插话）
         没有"判停"和"打断"这两个事件，它们只是采样结果
```

**判别标准**：系统里有没有"回合"和"话筒归属"这两个显式概念。半双工和可打断的半双工都有，区别只在说话时听不听；原生全双工没有，用户和 agent 的重叠、附和、抢话都是模型直接生成的。

## 2. 两种路线

### 2.1 原生全双工：moshi

```
 用户音频 ──► Mimi 编码（12.5 Hz，每帧 80 ms，8 个码本）──┐
                                                           ▼
                         ┌─────────────── 每 80 ms 一步 ────────────────┐
                         │ Temporal Transformer（7B）读：用户 8 码本      │
                         │   + 自己上一步的 8 码本 + 内心独白文本          │
                         │ 采样 1 个文本 token（自己要说的话；可为填充）   │
                         │ Depth Transformer 以它为条件生成自己的 8 码本   │
                         └──────────────────────────┬────────────────────┘
                                                    ▼
                                      Mimi 解码 ──► 逐帧下发播放
```

- 两路音频流（自己、用户）加一路文本流。文本流是模型对**自己**要说的话的转写（"内心独白"），**不转写用户的话**。
- 沉默就是文本出填充 token、音频出静音码。所以"判停"和"打断"不是系统事件，唯一接近判停旋钮的是采样偏置 `pad_mult`（把填充 token 概率乘上 `exp(pad_mult)`，让模型更倾向不说话）。
- 延迟（仓库自述）：理论 160 ms（80 ms 帧 + 80 ms 声学延迟），L4 上实测低至 200 ms。

作为产品上游的限制（读代码与 FAQ 得出）：

| 维度 | 现状 |
|---|---|
| 语言 | FAQ："Moshi only speaks English" |
| 系统提示 / 上下文注入 | 不能。协议定义了 Text 消息但只作输出，服务端收到非音频消息直接丢弃 |
| 工具调用 | 没有 |
| 会话时长 | Rust / MLX 实现用固定缓冲，FAQ 写明约 5 分钟后停止说话是预期行为 |
| 并发 | Python 服务端一把全局锁，同一时刻只服务一个连接；Rust 服务端每 socket 一个循环，无批处理 |
| 换声音 / 人设 | 要微调（FAQ 说暂不支持；README 指向 moshi-finetune，加载器支持 LoRA） |
| 出声前审核 | 文本 token 只比声学码本早 1 步（80 ms），没有审核窗口 |
| 回声 | 真全双工一定听到自己的声音；网页端靠浏览器 `echoCancellation`，命令行客户端没有 AEC |

同类的还有 MiniCPM-o 4.5（可自托管，协议里有 `listen / speak` 两种输出，模型自己切换），但没有 function call，会话建好后不能改，也不能注入历史（据 qwen-audio-agent 里的接入代码）。

### 2.2 组装式：unmute

```
 浏览器 Opus ──► 后端 ──► STT（会话级长连接，说话时也持续送帧）
                            │ 词 ──► 追加到 user 条目
                            │ 停顿概率 prs[2] ──► > 0.6 判停
                            │ 用户在 agent 说话时开口 ──► interrupt_bot()
                            ▼
                     LLM 流（任意文本模型）──► 逐词送 TTS ──► 按实时节奏释放（超前 ~0.32 s）
                                                      │
                                                      └─► 已播放的词写进 assistant 条目
```

unmute 是"让任意文本 LLM 能听能说"的薄编排层：Kyutai 流式 STT + 文本 LLM + Kyutai 流式 TTS。从链路看它是 [级联](cascade.md)，它的"双工"来自三点：

- **STT 一直开着**，agent 说话时也在听，判停用的是 STT 模型自带的停顿预测（系统提示里称之为 semantic VAD，具体语义待确认）。
- **打断有两条触发**：agent 说话期间 STT 的停顿概率降到 0.4 以下（会话开头 3 s 内不允许，因为回声消除还没收敛；`unmute_handler.py:UnmuteHandler.receive`），或 STT 出了词（`_stt_loop`）。unmute 没有独立的 VAD 模型，前者只是借 STT 停顿预测充当声学打断；两条路径都走 `interrupt_bot()` 并发出 `unmute.interrupted_by_vad` 事件，事件名里的 "vad" 容易误导。打断时取消 LLM、TTS 两个任务，**换掉输出队列**，让旧协程推不到新队列。
- **用历史长度当代际**：开始生成时记下历史长度，历史一变长（用户插话）就视为被打断，LLM 循环、TTS 循环、写历史三处都检查。

它仍然是轮流说话：不会生成附和、不会和用户重叠。这正是大多数产品要的"边听边说"。

小智固件的 `realtime` 模式是同一路线在硬件上的版本：需要设备端 AEC，说话时不关麦克风继续上行。但在设备端 AEC 下，服务端要等 ASR 出完整一句才打断，打断发生在判停 + 识别之后；`manual`（按住说话）模式明确不做自动打断。

## 3. 适合与不适合

| 路线 | 适合 | 不适合 |
|---|---|---|
| 原生全双工 | 英文闲聊、体验研究、需要附和与重叠的"像真人"演示；给产品团队一个"真全双工值不值得"的直观感受 | 需要工具、事实、审核、中文、长会话的任何产品；按键说话的设备（模型一直在听、自己决定开口，与按键模型冲突） |
| 组装式（可打断的半双工） | 开放麦通话、免按键的音箱和 App；想要自然打断又要保留工具和上下文控制 | 没有可靠 AEC 的硬件（误打断）；高噪声、儿童场景（误触发多） |
| 半双工（按键） | 无 AEC 的低成本硬件、儿童、户外噪声；需要确定性边界的场景 | 追求通话感的产品 |

## 4. 关键取舍

| 维度 | 原生全双工 | 组装式 | 按键半双工 |
|---|---|---|---|
| 响应延迟 | 最低（仓库自述 ~200 ms） | 取决于级联或 S2S 的首音 | 从松键算，没有判停等待 |
| 自然度 | 最高：附和、重叠、抢话 | 中：能打断，不会附和 | 低 |
| 可控性 | 几乎没有：只有采样偏置和强制状态 | 高：每段都在自己手里 | 最高 |
| 工具 / 上下文 | 无 / 最差 | 与底层链路相同 | 与底层链路相同 |
| AEC 要求 | 必须 | 必须，且播放期间常开 | 不必须；但播放期间仍可能有回声混进上行，有条件仍建议做（见 [audio-preprocessing](../03-mechanisms/audio-preprocessing.md)） |
| 误打断风险 | 由模型学 | 要自己过滤：保护窗口、最短时长、附和语、咳嗽 | 无（只认按键） |
| 成本 | 自托管 GPU，单连接或低并发 | 与底层链路相同，外加持续上行和 VAD | 最低 |

### 4.1 组装式的工程难点

**AEC 只能在扬声器所在的机器上做**。服务端拿不到扬声器参考信号；aiortc / Pipecat / LiveKit 三个服务端框架里唯一开 AEC 的是 LiveKit 本地 console 模式，因为只有它拿得到参考信号。小智的设备端 AEC 需要硬件回采通道，只对白名单板子开放，默认关闭。

**误打断过滤**要在冲刷之前完成。LiveKit 的参数可作起点：`aec_warmup_duration=3.0 s`（与 unmute 的"开头 3 s 不许声学打断"同一考虑）、`min_duration 0.5 s`、`false_interruption_timeout 2.0 s`。附和语（"嗯嗯"）和咳嗽要过滤，否则 agent 会被自己的听众打断。

**判停与打断放在服务端**，客户端不因本地 VAD 自行停播（否则端云状态不一致）；代价是停播要等一个往返加过滤时长。WebRTC 客户端几乎没有播放缓冲，服务端清自己的队列即可生效。

**按播放位置截断上下文**：说话中被打断，只有用户听到的部分进历史。unmute 写进历史的是 TTS 按播放时刻回吐的词。

## 5. 和其他决策的关系

- 全双工是"说话时听不听、谁决定开口"这一维，和 [cascade](cascade.md) / [s2s](s2s.md) 那种链路分类正交。组装式全双工可以建在级联、半级联或 S2S 之上。
- 按键模式和开放麦模式应当是**同一个回合状态机的两种配置**，差别只在边界来源（按键 vs VAD），见 [turn-model](turn-model.md)。
- 打断后谁还能出声、旧音频怎么清，见 [floor-control](floor-control.md)。
